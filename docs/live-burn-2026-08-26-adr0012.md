## C1 fails, and the confirmation flow is not why

The audit chain §7 asks for is **complete and in order on the durable log**:

```
confirmation.requested (6) → confirmation.accepted (12)
  → gate.evaluated(pre_action, pass, lease_id='La3564ab2') (14)
  → action.dispatched (16) → action.result_observed (18)
```

The lease was minted, carried the frozen snapshot's target, passed the full
re-run gate, and rode into dispatch. Zero LLM calls happened on the accept turn.
Everything ADR-0012 built worked.

Then `write_file_handler` refused, correctly:

```
code=target_not_found
"write_file: /Users/alllllenshi/Desktop/jarvis-burn-shopping.md does not exist;
 mode='append' requires an existing file"
```

**The LLM chose `mode="append"` for a file that does not exist — 8 times out of
8, across both attempts, with no exception.** Attempt 2 retried C1 four full
rounds (fresh runtime root, same utterance) and got `append` every round. It
never once chose `create`.

The mechanism is visible on the logs, not a guess. In two of the rounds the LLM
first tried to check:

```
action.proposed  read_file  target="桌面上的 jarvis-burn-shopping.md"  ref=null
gate.evaluated   refuse     "entity_trusted: entity_required: read_file demands
                             a resolved target"
```

That refusal is a **resolution** message, not an **existence** one. The LLM
cannot tell "this file is missing" from "I named the target badly", and one of
the runs said so out loud in its own draft: 「我刚才尝试先读取文件，但当前工具没有
成功解析这个目标文件，所以还没有看到原文件内容。」 `write_file`'s mode contract
(`create` refuses an existing file; `overwrite`/`append` require one) demands
exactly the distinction the tool surface refuses to give it.

Consequence for the row: `~/Desktop/jarvis-burn-shopping.md` **was never
created**. There is no burn artifact on the Desktop, because the burn never
successfully wrote one. Nothing else under Allen's home was touched.

This is a `write_file` tool-surface gap (ADR-0012 D1), not a confirmation-flow
gap — but it is the gap that keeps §7's flagship row red, and it is Allen's to
decide on, not the burn's to patch.

## The larger finding: the prompt's prose ask preempts the machine ask

**Of 20 ask utterances across the session, 10 produced a `confirmation.requested`
and 10 produced nothing at all.** The other half came back as *prose*:

```
待确认操作：向 `桌面/jarvis-burn-shopping.md` 追加一行 `买牛奶`。
待确认操作：append  \n目标：桌面/jarvis-burn-shopping.md  \n内容：买牛奶
待确认操作：\n- 目标：…\n- 内容：买牛奶\n- 模式：优先追加；若文件不存在则新建
```

`tools=[]`, `attention_channel=queue_review`, no `action.proposed`, no
`confirm_required`, no `confirmation.requested`, no projection slot, no armed
grammar. Had Allen then said 「可以」, the grammar hook would have been inert and
the turn would have fallen through to an ordinary LLM turn — exactly C3's shape,
except nobody intended it.

The cause is in `prompts/jarvis_v1.md`, which ADR-0012 D7 deliberately leaves
untouched:

- `<intent_and_routing>` — "Ask for confirmation before risky, persistent,
  external, or hard-to-reverse actions."
- `<action_safety>` — "Confirm before actions with persistent, destructive,
  external, or hard-to-reverse effects, including: writing or overwriting
  important files unless Allen explicitly requested that exact edit"

ADR §1 called those four instructions "decorative" because no machine could
receive the answer. The burn shows they are **worse than decorative**: they
compete with the machine ask and win about half the time. D7's claim that they
"become true by machinery, not by editing" holds only on the turns where the LLM
proposes the tool.

Attempt 2 handled this by retrying the ask (up to 4 fresh attempts per row,
same utterance, every attempt recorded) until one produced a
`confirmation.requested`. C2 needed 4 attempts, C6 needed 3, C1/C3/C4 hit on
their first. **The five green rows are green on the confirmation flow itself;
none of them is a claim that the ask arms reliably.** ADR §7's own
`prompt-side interface notes (only if live burn shows need — never as behavior
patch)` defer clause is now live evidence, not a hypothetical.

## Deviations, declared

1. **C1's write target is `桌面/jarvis-burn-shopping.md` → `~/Desktop/…`, not
   "scratch 的 shopping 文件".** `config/file_targets.yaml` has no `scratch`
   bookmark, and a bare natural-language target deliberately does not resolve
   (Step 4 erratum E10/E11; `resolve_write_target`'s own docstring names this
   exact example). The `桌面` bookmark exists. The utterance used verbatim in
   every attempt was 「帮我把『买牛奶』写进 桌面/jarvis-burn-shopping.md」 — never
   varied, never re-worded to make a row pass.
2. **Retries, not rewording.** Attempt 2 retried the *same* utterance on a fresh
   runtime root when the ask produced prose instead of a proposal. Every attempt
   — hit and miss — is in `burn_adr0012_v2_out.json`.
3. **Row independence via separate runtime roots.** Not one session log, six.
   The single-slot projection makes a shared log meaningless for these rows.
4. **C3's shortened TTL is `confirmation.ttl_ms = 3000`** (default 600000),
   injected through the config key Step 5 added — no code touched. The row slept
   4.0 s before answering.
5. **Only one real file was ever in scope for writing**
   (`~/Desktop/jarvis-burn-shopping.md`), and in the end nothing was written at
   all. Every non-C1 row snapshotted `(exists, bytes, mtime_ns)` before and
   after and asserted it did not move.

## One harness bug, caught the ADR-0011 way

The first verify pass reported `gate.evaluated optional key 'lease_id'
declared=False`. The registration was fine — the assertion read
`optional_payload_keys`, and the field is `optional_payload`. Same class of
mistake as ADR-0011's `events_emitted` miss, caught the same way: assume the
assertion is wrong before the system is. Nothing in `jarvis/` was changed at any
point during this burn.
