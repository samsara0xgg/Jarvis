1. 定位

Jarvis 是 Allen 的私人 AI 运行时：安静常驻，持续维护 Allen 的工作、任务、agent、Mac 和房间状态；在 Allen 召唤时立刻恢复上下文；在必要时调度工具、agent 和硬件执行；所有重要行动都要可验证、可追溯。

1.1 它不是

  • 不是聊天机器人。
  • 不是普通 voice assistant。
  • 不是 Home Assistant 替代品。
  • 不是通用 agent framework。
  • 不是陪聊 companion 优先。
  • 不是为了服务多人或商业用户而设计的通用产品。

1.2 它是

  1. 私人工作 cockpit——让你随时知道项目在哪里、agent 在干嘛、哪些任务没收尾、哪些结果需要审核。
  2. 上下文恢复器——你说"接着昨天那个继续"，它能找到 branch、commit、session note、trace、未验证项，而不是问你"昨天哪个"。
  3. 任务与 agent 总管——Codex / Claude Code / Hermes 都是 worker。Jarvis 记录任务、派工、监督、收结果、验证、排队给你审核。
  4. Mac 操作层——它能读文件、看 git、看屏幕、管窗口、用 terminal、浏览器和 clipboard。原则：先观察，后行动，行动后验证。
  5. 个人记忆层——它记住你的偏好、项目决策、工作习惯、踩过的坑、常用路径和你对提醒/主动性的反馈。
  6. 房间身体——RPi5、XVF3800、ESP32、Hue、display 是它的感官和身体。它最终能根据你的位置、时间、光线、温湿度和当前 mode 调整环境。

1.3 核心价值

  1. 减少重复解释上下文——你不用反复告诉它现在在哪个项目、昨天做到哪、哪个 agent 干了什么。
  2. 减少任务管理负担——它帮你记录、追踪、收尾、验证、交接，而不是让你在一堆 session 和 terminal 里手动找。
  3. 减少环境切换成本——你从写代码到 review，从桌前到卧室，从工作到休息，Jarvis 能调整工具、语气、界面和环境。

1.4 产品北极星

Jarvis 不追求"替你做所有事"，而是追求"让你继续前进时几乎不需要重新装载上下文"。

1.5 最高原则

原则 1. 单用户优先——只为 Allen 优化，不为泛化牺牲体验。
原则 2. 状态优先于对话——Jarvis 的核心不是聊天记录，而是当前 state：工作状态、任务状态、agent 状态、Mac 状态、房间状态。
原则 3. 证据优先于自信——agent 说完成不等于完成；工具返回成功不等于目标达成；Jarvis 要区分 reported、changed、tested、verified。
原则 4. 安静优先于打扰——默认安静维护状态。主动打扰必须有足够理由。
原则 5. 工具和硬件是身体，不是炫技——Mac 和房间硬件只是让 Jarvis 能感知和执行；产品核心仍然是帮助你管理状态和推进任务。

1.6 最终形态

  • 你坐到桌前，它知道你可能进入工作状态，灯光和界面准备好，但不烦你。
  • 你说"继续昨天那个"，它立刻恢复上下文。
  • 你让 agent 做事，它记录任务、跟踪进度、等你审核。
  • agent 说完成，它不轻信，而是查 diff、test、log、session note。
  • 你问"我是不是跑偏了"，它基于 commit、session、task ledger 给判断。
  • 你离开或睡觉，它降低打扰，把未完成事项排队，必要时调整环境。
  • 它越来越懂什么该提醒你，什么只该默默记录。

1.7 产品类别

Personal AI Runtime for Allen.
不是 assistant app，不是 agent app，而是一个私人运行时。它把 memory、tools、agents、Mac、hardware、tasks、modes 都统一在一个状态系统里。

2. 总架构

Jarvis 是 6-layer state-centric personal runtime。Identity 不在 LLM、prompt、mode、tools 或语音管线里——它在持续更新的 State Object 里。换 LLM、改 prompt、加 tool 都不动 identity。

3. Six-Layer Architecture

第一原则：Jarvis 是 state-centric personal runtime。它的 identity lives in durable State Object；其他层要么产生 events，要么读取 projections 做 decision，要么执行 gated action，要么把 state 呈现给 Allen。

这节是 Jarvis 的第一层产品架构。它不是 implementation order，也不是 MVP scope；它定义最终系统中每类对象属于哪一层，哪些能力不能越界。后续 schema、tool、surface、部署和 scenario 都必须回到这六层校验。

3.2 Phase 1: Constitution / Identity

Constitution 层只回答 Jarvis 是什么、为什么存在、不能变成什么。它不负责字段、表、tool schema、UI layout、Mac/RPi 拓扑或 prompt wording。它的作用是给后续所有工程设计设定不可协商的方向。

3.2.1 Locked constitution

C1. Allen-only personal runtime. Jarvis 永远先服务 Allen 单人，不为多人协作、商业化、通用 onboarding 或陌生用户可解释性牺牲私人化。它可以极度偏向 Allen 的项目、房间、Mac、习惯和表达方式。
C2. State Object is identity. Jarvis 的 identity 不在 LLM、prompt、router、agent loop、tool registry、voice pipeline 或 Inherent UI。它存在于持续维护的 Allen standing state。
C3. Reduce context load and task load. 核心价值不是泛化聊天，而是让 Allen 少重复解释：昨天做到哪、哪个 agent 在干嘛、哪些任务没收尾、哪些结果未验收、当前项目有没有跑偏、下一步先做什么。
C4. Supervisor, not primary worker. Jarvis 负责调度、监督、验收、整理状态。复杂工程执行主要交给 Codex / Claude Code / Hermes 等 worker。Jarvis 主 LLM 默认不应拿到 patch / write_file / terminal 这类 executor 工具。
C5. High privilege must be evidence-bound. Jarvis 可以拥有很高权限，但所有重要行动都必须受 policy、risk、confirmation、claim/evidence 和 invariant gate 约束。工具成功、agent 自报、LLM 自信都不能单独证明目标达成。
C6. Surfaces are replaceable; continuity is not. Voice、Inherent、browser UI、notification、OLED、ambient light 都只是 surface。今天可以换 voice provider，明天可以换 UI，但 State Object 里的 continuity 不能断。

3.2.2 Product non-goals

  • 不是普通聊天机器人，也不是普通 voice assistant。
  • 不是 Home Assistant 替代品；home automation 是身体的一部分，不是产品本体。
  • 不是通用 agent framework；Codex / Claude Code / Hermes 是 worker，不是 Jarvis 的 identity。
  • 不是 Cursor / IDE 竞争者；Jarvis 99% 情况下不亲自写复杂代码。
  • 不是多人协作 SaaS；权限和 UX 优先服务 Allen 的 N=1 工作流。
  • 不是陪聊 companion 优先；语气和人格服务状态管理，不反过来支配系统设计。

3.2.3 Success definition

Jarvis 成功不是因为它“更像人”或“会更多工具”，而是因为 Allen 可以更少重新装载上下文、更少手动追踪任务、更少在 session / terminal / notes / agent report 之间找状态。

Success =
  continuation without re-explaining
  + task / agent state visible
  + claims separated from evidence
  + actions tracked to completion or timeout
  + surfaces show freshness and uncertainty
  + work/home domains degrade predictably

3.2.4 Downstream constraints

  • 所有模块都必须围绕 event / projection / evidence 设计，不能把聊天历史或单次 prompt 当系统本体。
  • 所有 executor 能力必须区分 supervisor scope（jarvis_llm + observer）和 worker scope（worker_agent）。Caller principal canonical list 见 §3.5.2 和 §14.3。
  • 所有重要输出必须能降级成 “reported / observed / executed / verified / accepted” 这类证据语言。
  • 所有 UI 和 hardware 都只能读 projection、emit event 或执行 gated request；不能拥有 truth。
  • 所有长期学习都必须先通过 memory policy，不能把 current mutable state 写成 stable personal fact。

3.2.5 User Contract

Allen 跟 Jarvis 之间是有方向的隐性契约，不是 EULA，也不是 SLA。它约束 Jarvis 的 default behavior 和 Allen 的合理 expectation。

Jarvis 对 Allen 的承诺：

  • 安静优先：默认不打扰；主动开口必须有 evidence 和 reason。
  • 状态可见：Allen 想知道任何当前 state（task、agent、mode、device、domain）都能查到，带 freshness。
  • 不自证：完成 / verified / 可信都不被自然语言夸大；输出受 evidence 等级约束。
  • 跨 session 不丢上下文：Allen 说 “接着昨天那个继续” 时不需要重新解释。
  • 永远 N=1：所有 trade-off 优先 Allen 的工作流和习惯，不为通用化让路。

Allen 对 Jarvis 的承诺：

  • 持续给反馈：accept / reject / correct / dismiss 这些信号是 Jarvis 学习的唯一来源。
  • 明示偏好：long-term preference 通过明确表达进入 Memory，不期待 Jarvis 凭对话猜。
  • 接受 evidence-bound 措辞：“reported, not verified” 不是不确定，是诚实。
  • 不期待泛化能力：不要求 Jarvis 在 stranger / multi-user / 陌生 domain 表现得专业。

3.2.6 Autonomy Philosophy

Jarvis 的自主性沿 5 个 axis 独立调节，不是一个 “autonomy slider”。

3.3 Phase 2: State Object

State Object 是 Jarvis 的持久身体：它定义 Jarvis 能知道什么、相信什么、追踪什么、记住什么。它不负责推理和执行。

3.3.1 Event Log 是唯一持久事实入口

所有持久变化都必须通过 event 进入系统：voice input、agent report、tool result、git observation、mode switch、task update、user feedback、sensor event、surface response、cross-domain imported event。

No state without event.

不能出现 LLM 直接把 action 标成 done、Projection 被手工改写、UI localStorage 变成 truth。正确路径是 emit canonical events（e.g. action.result_observed、confirmation.accepted、memory.proposed，完整 schema 见 §5.4 Event Type Registry），再由 projection 推导当前信念。

Events 不可变。修正、反转、撤回必须通过 append 新事件表达（correction.X、supersede.X、revoked.X），原 event 永不被改写或删除。Projection fold 按 supersede 链生效；audit trail 始终完整。这保证 replay 一致、并发安全，不会因为后悔某条 event 把 history 改成另一个版本。

3.3.2 Projection 是只读派生信念

Projection 不是事实源，而是从 events fold 出来的 current belief。它可以 materialize、cache、rebuild、incrementally update，但不能被 LLM / tool / surface 直接写。

Projection作用

Pending Confirmations等待 Allen 回答的 confirmation request。

边界：Situation Packet 不是 State Object 的原始 projection，而是 Runtime Decision 的 turn-time export；Personal Profile 是 Memory Projection 的一个 view；Mode Preset Table 是 config/spec，不是 State Object。

3.3.3 Claim / Evidence（retired）

Retired by ADR 0019（2026-09-19）。claim.*、evidence.attached、Claim/Evidence projection 与 attach_evidence API 已从代码删除。Tool result 现在就是 action.result_observed 的 payload，原样进入下一轮 tool-result message，不解释、不评级。Freshness / TTL 语义只保留在 Memory（3.3.5）和 ImportedEvent（3.7.5）。

3.3.4 Task / Session / Run

Task     = 跨天、跨 session、跨 agent 的持久目标（ADR 0019 后由 Codex thread 持有，Jarvis 不折叠）
Session  = 一段交互 / 对话 / 工作片段
Run      = 在某个 task 上的一次推进尝试

ADR 0019 后 Task 不是 Jarvis 折叠的对象：工作目标和进度由 Codex thread 持有（§15），Jarvis 只保留 action 事件。Session 仍只是交互容器，不是主骨架。

3.3.5 Memory 是长期 projection，不是 current state

Memory 只保存长期稳定、可复用、能降低 Allen 重复解释成本的知识。它可以保存偏好、项目长期决策、工作流习惯、稳定 alias hint；它不保存当前 task 状态、当前 branch、当前 device state、agent 是否完成、raw transcript、raw sensor stream、未验证 claim、secret 或 full command output。

Memory 写入不是 State Object 自己决定。Runtime Decision 产生 memory candidate，检查 memory policy、stability、evidence、secret boundary 后 emit event；State Object fold 成 Memory Projection。

Writes reject oversized item metadata before committing, so it remains retrievable. Knowledge statement limit is 4,000 characters, todo title 500, briefing content 16,000, and source refs at most 20.

Updating a todo cannot replace its sources and does not revalidate previously accepted references. Knowledge requires at least one source; existence is provenance, not verification. Contradictory uncertain claims should be saved as needs_confirmation rather than replacing accepted user facts as verified truth. Queries open an existing WAL-aware read transaction, never create/migrate the source, and never run Git, screenshot tools, an LLM, or a second collector. Missing/unreadable/incompatible TimeSink stores report app coverage=unavailable without suppressing Git results.

TimeSink GRDB timestamps are interpreted as UTC and stored with millisecond precision; every bound is rendered in that same text form (rounded up for < and >=, down for > and <=) so SQL compares instants, never strings of different length. The requested window is [from,to). A span is the half-open [start,end) and is selected when start<to and end>from; a capture is the closed set of observation instants [at,ended_at] and is selected when at<to and ended_at>=from (an instantaneous capture exactly at from is inside); a state event is selected when from<=at<to. Adjacent windows partition every row. A nonzero span is one row [ref, start, end, app, text]: ref s<id>:<rev> (rev = the first 8 hex digits of the 32-hex row revision), start and end as local clock times (HH:MM:SS in the offset of from, prefixed MM-DD when not on the page's date and YYYY-MM-DD when not in its year), the app's dictionary letter, and text = window title plus the site domain in parentheses when the title does not contain it, at most 120 characters. The header is code-rendered and shared by every row of the page: apps maps letters A, B, ..., Z, AA, ... to [name, bundle id] in order of foreground_s; totals per letter cover the whole window regardless of paging: foreground_s is the seconds the app was frontmost per spans clipped to [from,to) with overlapping spans merged, spans and screen_rows count the matching rows, first/last are the clipped span bounds. A total names only the sources the query read: foreground_s, spans, first and last appear only when app is among the sources and screen_rows only when screen is; an unqueried source has no total, never a zero. An app filter reads both TimeSink sources (spans and captures) whatever sources lists, keeps rows whose app name or bundle id contains the text case-insensitively, excludes Git rows (coverage.git says so) and reports app_filter_matches per source; a filter that matches nothing also reports apps_in_window, the distinct [name, bundle id] pairs the source saw in the window, so a guessed name is retried rather than read as absence. summary_only returns the header, totals and state without rows. read_activity returns the exact saved row as paged JSON; stored_timestamp_timezone=UTC; its source_refs carries the full timesink:<store>:<id>:<rev> reference, which the row ref plus the page's store also yields; a saved reference may carry 8 to 32 revision digits (prefix match). Full values remain in the detail reader. Jarvis collects no page contents, screenshot or OCR itself. TimeSink's suppressed incognito fields remain suppressed.

Screen captures are TimeSink's capture rows (ADR-0022): one row per distinct front-window content inside one continuous observation segment. TimeSink extends a row's lastSeenAt only while the same window stays in front; leaving the window and coming back, an excluded app, and every lock, sleep, stop, pause or resume signal (however short, with a 5 s tick silence as backstop) each start a new segment, so unchanged content seen again becomes a new row and the stretch in between is never attributed to the old one. A capture is one row: ref c<id>:<rev>, start = at, end = ended_at, the app letter, and text = window title — the start of the OCR text, at most 200 characters (an excerpt; the page's notes say so, never presenting it as the full text). ended_at is lastSeenAt (basis last_seen) unless a row written before segments existed crosses a recorded lock/sleep/pause/stop event or the start of another app's span, in which case ended_at is that recorded instant (the true end is no later; nothing is invented), the row's end carries a trailing !, and read_activity reports ended_at_basis=interrupted with last_seen_at keeping the stored value. read_activity returns the full OCR text as paged content_format=text with app/window identity, span_id, ended_at, ended_at_basis, last_seen_at, image_available (the file exists now), image_path (absolute, null once the image aged out or was deleted) and the full timesink-capture:<store>:<id>:<rev> source_refs. A store without the capture tables reports screen coverage=unavailable without affecting app results.

App coverage=partial means saved spans are readable, not that the requested interval was continuously observed. Coverage includes latest_span_end, observations_in_window, time_basis=span_overlap and gap_reason=unknown for spans. Any query touching app or screen also returns TimeSink's own reasons (idle/active, lock/unlock, sleep/wake, pause/resume, start/stop, screen_denied): state_at_start is the latest event before from of each independent group (start/stop; lock/unlock; sleep/wake; idle/active; pause/resume/screen_denied; a wake never implies an unlock), so a lock before from with no unlock inside explains an empty window; state_at_start and state_events are [time, kind] pairs in the page's clock; state_events are the events inside [from,to) in time order, paged with the rows inside the same cursor and page budget, never truncated silently, with state_events_total the window's count; state_coverage.status is partial with events_in_window when the stateEvent table is readable, unavailable when it is not, and unknown when neither app nor screen was requested. Spans, captures and state events of one page come from one read transaction. Gaps not explained by a state event remain unknown, and tracked durations cannot prove attention or task completion. Mixed queries report time_basis=source_specific, ordering Git by observed_at and app spans and captures by occurred_at. A Git observation is one row: ref g<uid> (source reference event:<uid>), start = the observed time, end empty, app = git, text = repository path: subject, with the commit time appended when it differs.

A page holds as many rows as its 48,000-character budget allows (rows first, then state events; a first page also carries notes explaining text, refs, times and totals once). Activity cursors pin the append watermarks (snapshot for the event log; span, capture and state event IDs for TimeSink), the row and state event offsets, and check a digest of the selected TimeSink span and capture revisions. Later inserts are omitted from continuation; changed/deleted rows or source replacement produce invalid_cursor and require restarting the query; a cursor issued for other arguments is cursor_mismatch. TimeSink references bind database identity, row ID and content revision; a capture's revision covers its identity, the time basis it reports (at, lastSeenAt and the interruption a legacy row is clipped to), app, window, title, span and OCR text but not image retention, so a reference saved into knowledge, todos or a briefing stays readable after the image aged out. A short row ref names the configured store and is a lookup key, not a saved source reference. Changed detail reads return source_changed, deleted rows return not_found. This is revision validation, not historical version archival: a saved reference can become unavailable after the independent source changes. Coverage freshness metadata may advance between pages without changing the selected rows.

Briefing coverage has records/git/app/screen/agent/todos/knowledge entries with values available/partial/unknown/unavailable/not_implemented; omitted entries default to unknown. coverage_basis=reported_by_generator distinguishes it from measured collector health. Saving a briefing never marks it delivered or heard. The daily work report below is the one writer that saves a briefing without the model choosing its fields. Background consolidation, collectors, scheduler, wake-time catch-up, delivery deduplication and Live write-policy integration are separate capabilities.

Current work state (ADR 0023). One record, folded as the latest work_state.revised event (owner L2, actor jarvis_llm, schema version 1; payload item, trigger = dashboard | conversation, action_id?). item carries id=work_state, version, created_at, updated_at, analyzed_at, observed_until (the latest TimeSink instant the analysis saw, null when none), evidence {fingerprint, window {from, recent_from, to}, coverage {app, screen, state, records, todos, knowledge, git}, counts}, now (a claim or null), activities[] (claims with progress), links[] (kind todo | discussion, ref = todo id or record:<id>, title, note, basis), uncertainties[], note (the user's statement fed into this analysis), question, model. A claim is {text, basis, refs} where basis is stated (Allen said it: an Allen-authored record or the note), observed (app/window/screen data) or inferred (the model's reading), and refs are the durable source references (record:, event:, timesink:, timesink-capture:, git:, codex-session:, note) behind it. The rules are enforced on save, not by prompt: refs the model did not receive are dropped; a stated claim without a Allen-authored record or note ref and an observed claim without a TimeSink ref become inferred and are counted in uncertainties; a record with inferred claims always carries an uncertainty; now is kept only when it cites screen observations inside the recent window (window.recent_from..) and carries as_of = the newest cited screen instant so it is never shown as "current" without its instant; evidence.limits (truncation, unreadable sources, unconfigured Git) are appended to uncertainties. Writes check expected_version; a stale writer gets version_conflict and the newer record stands. The analysis never changes todos: a link is a claim, not a completion.

The refresh workflow is one runtime job shared by refresh_work_state and POST /inherent/work-state/refresh; GET /inherent/work-state returns the same view without analysing. It gathers bounded evidence: the defaults are today's spans aggregated per app and window, the last 2 h of screen captures with OCR excerpts, today's earlier captures grouped per window, TimeSink state events, 48 h of memory.db records, open todos, active knowledge, today's Git observations and the note; when a question is given its topic terms (stop words removed, CJK bigrams added) also retrieve matching older records and captures (14 days) and rank todos and knowledge, so "之前说的事情进展如何" reaches the relevant history without tools. Every cap that clipped material is written into evidence.limits and into the material itself. "Today" and every rendered time use work_state.timezone (unset = system local). The fingerprint covers the bounded material, its source revisions and durations, state events, coverage, local day, record ids, todo/knowledge versions, Git observations, the note and question. Extending rows change the evidence revision; the request clock alone does not invalidate a result; the model is called only when it differs from the saved record's or force is set, otherwise outcome=reused. Empty evidence is outcome=no_evidence and writes nothing. The model receives only the report tool and keyed text, never images; screen and record text is material, not instruction. A refresh whose input (question, note, force) equals the running one joins it (joined=true); a different input waits and then runs on the record the first saved, so a new question or fact is never answered with a result computed for another. Each run returns its own immutable result to its callers. Malformed model reports fail schema validation rather than saving an empty replacement. A failed call keeps the previous record (outcome=failed, error). No refresh runs on opening the dashboard, on ordinary turns or in the background.

Background sync is timesink.state_observed (owner L5, actor observer): every observer.timesink.poll_interval_s (default 300) the daemon reads the store head — status ok | unavailable, identity, span/capture/state max ids, span_latest_end, capture_latest_seen, state_latest {at, kind}, observed_at_ms, reason? — and emits only when the head changed; the baseline is recovered from the log, so a restart or a wake adds at most one row and never re-accumulates an activity. The read view reports three clocks apart: freshness.checked_at_ms (last read, including unchanged polls and manual refreshes), freshness.latest_observed_at (newest span end / capture last-seen the poll found) and freshness.analyzed_at; a successful poll is not fresh data. The check clock is maintained in memory on every read, with the persisted observation as a fallback after restart. The head is a collector-health trail; it never triggers decide() and never calls a model.

Task skills (ADR 0024). A skill is a directory jarvis/shared/skills/<name>/ holding SKILL.md — frontmatter with name and description, then the instructions — plus optional references/*.md appended to those instructions in filename order. load_skill(name) reads it at import time, so a malformed skill fails at boot, not at use. The frontmatter description is the tool description the decision model reads and the body is the system prompt of the task's own model call, so the trigger text and the instructions cannot drift apart. A skill carries instructions only: the procedure, the evidence caps, the tool catalog and every rule enforced on save are code in L2/L3/runtime. Skills are not discovered dynamically, are not user-editable at runtime, and never carry credentials or executable steps.

Daily work report (ADR 0025). One local calendar day, one saved briefing. daily_work_report and the runtime job behind it resolve the day in work_state.timezone (argument timezone overrides, unset falls back to the system IANA zone): no local_date means the previous local date, never now minus 24 h, and a future date is rejected. The window is the local [00:00, 24:00), cut at the request instant while the day is still running, and that cut is stated in the material and in the report. An existing briefing for that date and zone is returned unchanged (outcome=reused, no model call) unless regenerate is set, which writes the next version through save_briefing's own expected_version check, so a stale writer gets version_conflict and the saved report stands. Evidence is gathered once per run: the day's TimeSink spans aggregated per app and per window, its captures grouped per window and per hour (the longest OCR text of each group), TimeSink state events, that day's memory.db records, that day's commits read from every watched local repository (each local branch, filtered by committer time, marked on main or not) with the observer's project.commit_seen events folded in by SHA for the observation time, the Codex sessions with a turn inside the window (~/.codex/sessions, every file begun by that day and written since, cut to the window in the listing and in the details; first prompt and last reply, labelled as the agent's own account), plus open todos, active knowledge and the previous day's report as context that is labelled not-today. Commits are deduplicated by SHA across repository paths, each entry naming every path it was found in, and carry both their commit time and their observation time (or 观察器未记录) with a late flag when the commit fell on another local day. Every cap that clipped material names the omitted count and is written into the material and into the saved report, and every capture, window, record, commit and session of the day is a citable, searchable key whether listed or not. Empty evidence is no_evidence and writes nothing. The model receives the skill's instructions, the keyed material, and three tools: search_material, a keyword search over the whole day (capture text in the store; windows, records, commits and sessions in memory) returning up to twenty keys with a line of context, each marked with its length when it exceeds one detail; request_details, which returns the originals behind up to ten keys (full OCR text, exact record text, git show --stat of a commit, a session's prompts and last reply, or the stored span row, whose bare GRDB times are labelled UTC), the head of a long one unless around names a word, when the passage holding that word — for a session, the turn holding it — is served instead; and report_daily_work. Calls use tool_choice=auto. At most four model calls per run: two rounds in which the model may search or ask, after which it is told to report, and one retry of an unusable report. A malformed report fails the run without replacing the saved version, and a provider failure keeps it too (outcome=failed with the round and finish reason). The saved text is composed by code, not by the model: refs the model was not given are dropped and counted; an item's progress is one entry per part (code, tests, deployment, an application; a whole item is one unnamed entry), each with its own status and refs, so no single status covers development, tests and deployment; every part is labelled with what it cites — each same-day commit by short SHA and each Allen-authored record by its material key, or else Codex session self-report alone, screen and app records alone, or no valid reference — which asserts nothing about whether that source supports the claim. A completed part that cites neither is named by item number and part as an uncertainty, not relabelled; a user_next_steps entry that cites no Allen-authored record is removed from that section and quoted as an uncertainty; coverage, evidence counts and every material limit are appended as uncertainties. 核心摘要, the only section served onward, is the model's prose followed by the items with a completed part, by number and title, split by whether a same-day commit or an Allen-authored record stands behind that part, a mixed item carrying every part's status after its title (代码完成，部署进行中), and a count of the rest by their highest status, so a summary cannot outrun the body unnoticed. Each cited source is written out once, in 证据引用, and the body cites it by number; the first 20 are also saved as the briefing's source_refs, which the store checks on save (git:<repo>:<sha> with git cat-file, codex-session:<file> as a file), so every claim is re-checkable through read_activity / read_records, the repository or the session file. Saving a report still delivers nothing, and a suggestion inside a report creates no todo and triggers no action. Reports exceeding the composition budget fail without saving, preserving the previous version; no body or citation index is truncated.

3.4 Phase 3: Runtime Decision

Runtime Decision 是 Jarvis 的判断层。它读取 projection snapshots，组装 context，解析 policy，选择 route，决定 attention，提出 action，解释 result，并约束输出。它不拥有真相，也不直接执行副作用。

3.4.1 Event-triggered, not turn-bound

User turn 只是 trigger 的一种。Runtime Decision 也会被 agent.reported、action.timeout_assumed、surface.user_intent、confirmation.accepted、sensor.alert、scheduler.fired、cross_domain.response.received、domain_availability.changed 触发。

3.4.2 Stateless across invocations

Layer 3 不能把状态存在自己的内存里跨调用依赖。跨 invocation 的所有 state 必须回到 State Object、config/spec、artifact refs、domain availability 或可重建 cache。Layer 3 可以有 invocation scratchpad，但它不是 Jarvis identity。

3.4.3 Decision invocation model

trigger event
  -> load projection snapshot (high_water_mark=N)
  -> assemble consumer-specific packet
  -> resolve effective_policy
  -> choose route / decision engine
  -> produce plan / action proposal / text proposal
  -> pre-action / pre-emit gates
  -> dispatch gated ActionRequest to Layer 4 if needed
  -> interpret raw result into claim/evidence/action lifecycle events
  -> emit events

本次 decision 读取 projection version N；中途 read-only tool result 可进 working memory；side-effect action 必须写 durable lifecycle event；中途 append 的 events 不自动改变本次 decision 的 projection view。若需要 fresh state，必须显式 refresh 或开启下一次 decision。

Situation Packet 是给 decision engine 的裁剪版 context export，不是 State Object 的原始 state。Runtime Decision 可以组装 LLM Situation Packet、Surrogate Feature Packet、Attention Candidate Packet、Memory Write Context。

3.4.6 Intent Routing

Tier 0 regex、Tier 1 surrogate、Tier 2 cloud LLM、direct event path 都只是 route。Tier 0 命中 "关灯" 后仍要 resolve entity、check effective_policy、maybe confirmation、emit ActionRequest。Tier 1 surrogate 当前不是主线；没有 truth data 和 eval harness 前不该抢 state / tools / evidence 的工程窗口。Tier 2 cloud LLM 是 stateless, untrusted calculator。命名注：Tier 0/1/2 是 intent-routing tier，与 §3 的 Layer 1-6 是不同 namespace（见 §2 命名约定）。

3.4.7 Attention Policy

Attention Policy 是事件级干预层，不是 durable mode classifier。它读取 candidate event、effective_policy、urgency、confidence、risk、reversibility、timing、interruption cost、annoyance history、user feedback、freshness 和 domain availability，输出 silent_log、review_queue、badge、suggestion、voice_notification、interrupt、ambient_action、confirmation_request 或 delegate_agent。

Feasibility 决定：hard gates 必须 deterministic；channel scoring 可以是 local weighted formula；LLM-as-judge 只用于罕见边界情况；每个 candidate 都过 LLM 是 architectural fiction；Layer 3 做 attention candidate coalescing；physical surface mapping 在 Layer 5。

3.4.9 Tool-use intermediate results

本次否决 "turn 结束才一次性 emit 所有结果" 的纯方案。Read-only tool result 可以在 decision working memory 暂存，end-of-invocation batch emit；side-effect action 必须先 durable record lifecycle，再执行；action result / failure / timeout 必须写 event；projection snapshot 不在同一 invocation 内自动刷新。

Tool budget and answer (ADR 0030). The Tier 2 loop allows at most max_tool_iterations model requests that may propose tools (default 5). When the last of them still proposes tools, the runtime dispatches them and then makes one more request with no tools, carrying a runtime note (marked as not the user's words) that asks for the answer from the tool results already held, facts with their evidence first, unknowns stated. That request runs under the same cost recording, admission and cancellation checks as the loop's calls and is not counted against the tool budget. If it fails or returns no text, the turn ends with a fixed Chinese limitation, never an internal English error.

3.4.10 Entity hallucination repair protocol

  1. Exact canonical id / trusted alias：pass。
  2. High-confidence fuzzy + read-only / low-risk：silent repair。
  3. Medium confidence 或 side-effect：ConfirmationRequest。
  4. No match：same-invocation retry 最多一次，带候选 IDs。
  5. Second failure：fail closed 或 ask Allen。
  6. High-risk action：不允许 silent fuzzy repair。

3.6.5 Voice boundaries

Voice 同时是 input adapter 和 output surface，但两边都不能越界。

  • Interrupt: Voice 只执行 speak、suppress、duck、stop、resume；“该不该打断 Allen”属于 Attention Policy。
  • Fallback: TTS provider failure 必须走 surface fallback chain，不应吞掉 message。

Staging area 的 artifact bytes 留在 surface-side artifact store；State Object 只收到 staged_item_id、metadata、artifact_ref、TTL、consumption status。后续 “读这个图” 通过 staged_item_id 或 correlation_id 绑定。

3.6.9 Freshness / evidence / stale UX

State Object 是 Jarvis-observed belief，不是宇宙真理。Surface 必须把 freshness 和 evidence level 展示出来，否则 Allen 会误以为 UI 上每个状态都是实时事实。

  • Hue state: RPi reported lamp off 4s ago。
  • Agent status: last heartbeat 22m ago。
  • Task status: reported_complete, not verified。
  • Git state: refreshed just now / stale since wake。
  • Home domain: offline, queued request pending。

Surface view model 可以决定布局、排序、折叠和视觉强调；verified / reported / blocked / accepted 等语义必须来自 projection。

3.6.10 Presentation action vs world action

有些输出看起来像 action，尤其是 notification、voice、ambient light。必须分清：

Presentation actionshow badge、speak、render panel、ambient hint低风险，但仍受 AttentionRouting、rate limit、fallback 约束。
World actionturn off light、send message、patch file、spawn worker必须走 Layer 4 ActionRequest 和 full action lifecycle。

Hue 用作 ambient hint 和 Hue 真正改变房间状态不是同一件事；风险和 evidence 要分开记录。

3.6.12 Backpressure and coalescing

Coalescing 分两层：

  • Layer 3: attention candidate coalescing。多个相似 heartbeat / report / sensor event 在短窗口内合成一个 routing decision。
  • Layer 5: render-level coalescing。同一 subject / same surface / short window 内只渲染最新或聚合版。

Layer 5 可以防刷屏和优化视觉更新，但不能改变“是否该提醒”的 decision 等级。

Deviation — D6 lifecycle commentary: commentary delivery 不走上面两层 coalescing。它由 runtime observer 在 durable Event Log 上按 turn 封顶为每 turn 最多一句，见 ADR-0008 §10。

3.7.7 Cross-domain request lifecycle

MQTT / network reconnect 下不要承诺 exactly-once。正确模型是 at-least-once delivery + idempotent receiver。

sender:
  cross_domain.request.dispatched(request_id, target_domain, expires_at)

receiver:
  cross_domain.request.received(request_id, origin_domain)
  cross_domain.response.sent(request_id, result_ref)

sender:
  cross_domain.response.received(request_id, latency_ms)
  OR cross_domain.request.expired(request_id)
  OR cross_domain.response.late(request_id)

idempotency_key 用于 retry 去重。Receiver 看到同一 key 已处理过时，不重复执行 side effect，直接重发上次 response。

3.7.8 Mac sleep / wake protocol

Mac sleep 是 deployment layer 的核心现实问题：Mac 睡眠时 worker、Inherent、local tools、Mac event mirror 都会受影响。

  • Sleep 前 best-effort emit mac.sleeping(reason, in_progress_actions)，flush local events，并 cross-publish mac_going_offline。
  • 对 running worker / action 尝试 emit worker.suspended_by_sleep 或 action suspension events。
  • Sleep hook 不可靠：没电、系统强制睡眠、进程被杀都可能绕过 before-sleep。
  • Wake 后必须 emit mac.awake(slept_for_ms)，执行 mandatory reconciliation scan。
  • 所有跨 sleep window 的 dispatched/running action 若无 terminal event，必须 close lifecycle：worker.terminated_by_sleep、action.timeout_assumed、Limitation Claim。
  • Wake 后 Layer 5 / Inherent / mirror cache 重新 rehydrate，并处理 RPi deferred queue。

3.7.9 Scheduler / deferred execution

“明天提醒我”不能依赖 Mac 一直醒着。Scheduler 是 cross-domain deferred execution 的特例。

DeferredExecution:
  schedule_id
  owner_domain
  backup_domain
  fire_at

Mac 创建 reminder / deferred action 后可复制给 RPi。RPi 到点 fire；如果 Mac asleep，则按 delivery_policy queue、fallback 到 home surface，或等 Mac wake 后 flush。相关 events 包括 scheduler.scheduled、scheduler.cancelled、scheduler.fired、scheduler.expired。

3.7.10 IDs and event identity

Local SQLite 可以继续用 integer primary key 作为本地 row id，但跨域引用必须有 global sortable ID，例如 UUIDv7 / ULID。

local_id: domain-local integer
event_uid: global sortable ID
origin_domain: mac | rpi_home | edge_... | ...

Domain ownership 由 origin_domain 字段表达，不靠 ID prefix 推断。

3.7.11 Transport and network assumptions

当前假设 Mac 和 RPi 在同一个 trusted LAN，MQTT broker 在 RPi。MQTT 是 transport，不是真相。Rule: local commit first, then publish。

Remote access、VPN、多网络 federation、手机远程访问都不是当前 scope。不要提前把系统拖进 NAT、remote auth、mobile push 的坑。

3.7.12 RPi inference and scoped home policy

RPi 负责 deterministic local inference rules 和 scoped Layer 3 mini for home decisions，不运行完整 Jarvis cognition stack。高频 presence / ambient 逻辑应规则化、低延迟、可解释；复杂判断可以 defer 或 request Mac/cloud。

RPi:
  rule-based sensor inference
  scoped Layer 3 mini / home policy evaluator
  small home-only attention/action router
  no full work-context cognition

3.7.13 Artifact stores per domain

  • Mac artifact store: terminal output、test logs、screenshots、multimodal staged files、worker reports、diffs。
  • RPi artifact store: sensor snapshots、device logs、必要 audio snippets。
  • Event payload: summary、artifact_ref、content_hash、size_bytes、mime_type、retention_policy。

Replay must not load artifact bytes by default。Artifacts may expire according to retention policy；event 仍存在，但 evidence scope 会改变为 artifact unavailable / summary retained。

3.7.14 Backup, replay, migration, maintenance

Projection rebuild / migration / backup 是 per-domain system_maintenance responsibility。Mac maintenance rebuilds Mac projections；RPi maintenance rebuilds RPi projections。Mac CLI 不能直接修改 RPi projection files；跨域 admin request 必须由 target domain 本地执行并记录。

Config、mode preset、tool registry metadata、domain ownership map、surface fallback chain、MQTT endpoint、artifact retention policy 不是 runtime state。重要 config change 应 emit audit event，但不等于 current state 变化。

3.7.15 Offline / stale semantics

Domain offline / stale 是 first-class state：

domain_availability.changed
domain_projection.stale
cross_domain.request.deferred
cross_domain.request.expired
cross_domain.response.late

Mac asleep 时 Home domain 继续 ambient / sensor / Hue；RPi offline 时 Mac work cockpit 继续但 home control unavailable or queued；cloud LLM down 时 L0/local paths degrade；worker unavailable 时 task pending/blocked。Surface 必须显示 stale/offline，不假装 fresh。

3.8 Cross-Layer Invariants

1. State flows through events. 任何持久变化都必须能追到 event。
2. Events are immutable. 已写入 event 不可改、不可删；corrections / supersession / revocation 通过 append 新 event 表达，audit trail 始终完整。
3. Belief is derived, not commanded. Projection 只能 fold / rebuild，不能被 LLM、tool、surface 直接改。
4. Decision reads snapshots. Runtime Decision 不把 working memory 当 truth。
5. Execution cannot self-verify. Tool success / worker report 不能直接变成 verified completion。
6. Surface never owns truth. UI 可以缓存 layout，不缓存 active_task / task status 作为 truth。
7. Domains own only bounded authority. Mac 不直接拥有 Hue truth；RPi 不拥有 Mac repo truth；cloud LLM 不拥有任何 state。
注：本节只列 cross-layer 通用约束。其他 invariant 嵌入在 layer 描述内：high-risk action 必须 confirm（3.4.7 Attention + 3.5.12 SandboxPolicy）、no entity_id invention（3.3.7 + 3.5.12 sandbox）、no action without effective_policy（3.4.5 Effective Policy Resolver）、no memory as current state（3.3.5 Memory）、event payload bounded（3.3.9 + 3.5.11）。这些不是不重要——它们是 layer 内规则，不是跨层约束。

3.9 一句定稿

Jarvis is a state-centric personal runtime whose identity lives in a durable State Object. IO adapters convert the world into bounded events, Runtime Decision reads projection snapshots and produces policy-gated requests, Capability Execution performs those requests without self-verifying, Surfaces render projection-backed state without owning truth, and Deployment Domains federate physical ownership across Mac, RPi/Home, Edge, and cloud calculators without a single mutable global brain.
Jarvis 是一个以 State Object 为本体的私人运行时。IO adapters 把世界变成有界 events；Runtime Decision 读取 projection snapshot 并产生 policy-gated requests；Capability Execution 执行请求但不能自证；Surfaces 展示 projection-backed state 但不拥有真相；Deployment Domains 把 Mac、RPi/Home、Edge 和 cloud calculator 的 physical authority 联邦起来，而不是构造一个全局可变大脑。

4. State Object

Jarvis 在时间里的 identity。物理实现 = Event Log + Projections。

  • Event Log 是事实源（knowledge 层）
  • Projections 是当前世界的解释（belief 层）
  • 所有其他模块（Policy Resolver、Intent、Action Layer、Gates）都是穿过 state 的计算，不持有 state

5. Event Log

5.4.3 Migration plan

本节为 spec lock；完整 registry 填充按以下优先级：

  1. P0：ActionLifecycle 8 events（worker.*、claim.*、evidence.attached 已随 ADR 0019 退役）。
  2. P1（cross-domain 必需）：cross_domain.* 8 events + scheduler.* 4 events + mac.{sleeping,awake} + domain_availability.changed / domain_projection.stale。
  3. P2（surface / runtime trigger）：剩余 §5.2 enumerated entries（utterance.received、surface.*、multimodal.staged、sensor.alert、confirmation.*、memory.proposed）。

Cross-domain unknown / unregistered event 走 cross_domain.event_quarantined（见 §3.7.6），不 crash ingest 也不 silent drop。Schema version 不匹配同走 quarantine。

Registry 落地形态：本节给出 spec-level shape。实际实现可以是 SQLite 表、JSON/YAML 文件或代码常量，但 single source of truth 性质不可让步——projection 折用、L4 dispatch、cross-domain transport 都必须 read 同一份 registry，不能各 layer 各自维护副本。

5.4.4 Realtime request admission and trigger completion

response.request_admitted 是 L3 的请求准入事实，producer 为 jarvis_runtime，schema version 为 1。required payload 为 response_id、admission_id、kind；无 optional payload。source_event_id 引用该 response 的 response.started，correlation 使用 turn_id。它供 Recent Trace 和取消因果审计读取，evidence semantics 为 ack，cross-domain policy 为 local_only，artifact policy 为 none。它不证明 provider 已接收请求、产生输出或消耗费用。

turn.ended 的 version 1 注册增加 optional payload consumed_trigger_event_uid：标识此次已完成语义处理的输入 trigger，并与该完成事件一同提交。其 source_event_id 仍引用最后一个 gate。运行时检查 terminal trigger 是否已消费时，必须承认这个持久完成事实；后写的 operational consumption marker 失败不得使已完成 trigger 再次执行。未完成的孤立 trigger 仍可恢复。决策原因与迁移边界见 ADR-0008 D1 / D8。

9. Memory Boundary

第一原则：Memory 不是 Jarvis 的数据库。Memory 是 State Object 里的一个长期个人知识 projection——只保存能长期降低 Allen 重复解释成本的稳定个人知识。

它不保存当前状态，不保存任务进度，不保存原始事件，不保存完整对话，不保存 agent logs。

Memory 是从 Event Log、Obsidian、反馈历史中提炼出来的长期可复用 projection。它是 hint，不是 current truth。

9.1 第一性原则

Jarvis 需要记忆，是为了解决一个问题：

Allen 不想每次重新解释自己是谁、项目怎么做、偏好是什么、之前踩过什么坑、Jarvis 该怎么配合。

所以 Memory 应该服务于：减少重复解释 · 减少错误假设 · 减少不必要确认 · 延续长期偏好 · 保留稳定决策 · 改善 Jarvis 行为。

它不应该服务于：保存所有聊天 / 所有状态 / 所有任务 / 所有工具结果 / 所有 sensor 数据 / 所有 agent output——这些分别属于别的层。

9.2 Memory 和其他系统的边界

系统职责
Event Log记录历史，Jarvis 观察到什么
Codex worker thread持有工作目标和进度（ADR 0019，§15）
Session / Episode保留近期交互上下文
Obsidian人类可读的长期文档、研究、决策、产品宪法
Memory从上面这些提炼出来的长期个人化 projection

一句话：Event Log 记录历史，Codex thread 管工作，Obsidian 管长文档，Memory 管长期个人化。

跟 Event Log 的关系

Event Log 是原始观察历史；Memory 是从这些事件中提炼出的长期知识。

Event:
  2026-05-16 Allen dismissed "daily summary" reminder three times.

Memory:
  Allen dislikes unsolicited daily-summary reminders during coding sessions.

Event Log 是证据链；Memory 是长期结论。Memory 必须能回指 source events，但不能替代 source events。

跟工作状态的关系

工作目标和进度（running / blocked / finished）不进 Memory——ADR 0019 后它们由 Codex thread 持有，Jarvis 只观察。但工作结束后可提炼可复用 lesson：

Task fact:
  tools_v2 clipboard fallback was blocked because tools_v2 was not wired
  into jarvis.py chat path.

Memory:
  For Jarvis tool work, verify whether a tool is registered in runtime
  chat path, not only tools_v2 smoke path.

原则：work status stays with the worker；reusable lesson may enter Memory。

跟 Evidence Model 的关系

Memory 不能比 evidence 更强。如果 evidence 只说明"agent reported"，Memory 不能写成"已完成"。

错误：

Memory: clipboard fallback works in live runtime.

正确：

Memory: clipboard fallback implementation existed, but live runtime
        reachability was previously blocked by tools_v2 chat-path wiring.

Memory 必须继承 evidence 的 scope 和 limitation。

跟 Session / Episode 的关系

Session 是交互窗口。Session summary 帮助恢复连续性，但不是长期 memory。只有当 session 中出现稳定结论，才提升为 memory。

跟 Obsidian 的关系

Obsidian = canonical long-form knowledge
Memory   = compact operational hint + pointer

产品宪法等长文档应该在 Obsidian / HTML / doc 里。Memory 只需要记 pointer：

Jarvis Product Constitution exists at docs/product/jarvis-product-constitution.html.
Core positioning: Jarvis is Allen's private AI runtime.

不要把整篇文档塞进 Memory。

稳定个人偏好和习惯：

  • Allen prefers direct, concrete answers.
  • Allen dislikes unnecessary proactive chatter.
  • Allen wants Jarvis to be single-user and deeply personalized.

2. Jarvis Behavior Preferences

最重要的一类，直接改善 Jarvis 行为：

  • Say who reported what: a worker's report is the worker's, not Jarvis's verdict.
  • Use commit history and hot notes over stale docs.
  • Do not over-expand regex variants without data.
  • Prefer quiet maintenance over frequent notifications.

可有 pointer 到 constitution doc。

4. Workflow Patterns

Allen 常用工作方式：

  • Allen often uses Codex / Claude Code / Hermes as worker agents.
  • Jarvis work should say whether a result was observed by a tool or reported by a worker.
  • Session wrap-up should produce a concise handoff.

5. Reusable Lessons

从踩坑里提炼出的经验：

  • When adding a tools_v2 tool, verify both standalone smoke exposure and live jarvis chat-path exposure.

6. Entity Aliases / Stable References

谨慎存。项目路径、设备别名、房间名。但这类是可审计的 alias state（3.3.7），Memory 只能作为 alias source 之一：

最终控制设备仍要经过可审计的 alias 解析。

来自 Allen 显式 / 隐式反馈：

用于 Attention Policy，不直接用于事实回答。

9.5 Memory 写入流程（promotion，不是 dump）

不再用"每轮 LLM observer 随便抽 bullets"的模式。长期会膨胀、污染、互相矛盾。

  -> classify type
  -> attach source_event_ids / evidence
  -> check scope
  -> dedupe / supersede
  -> decide store / ignore / ask Allen

Memory Candidate 必须过 4 问

  2. 它是稳定知识，还是临时状态？ 临时 → 不存。
  3. 它有 source / evidence 吗？ 没有 → 不能强写。

9.7 Memory 和 Prompt 的关系

Memory 不应该完整 dump 进 prompt。正确方式：

  -> relevance filter
  -> Situation Packet hints (block 6)
  -> LLM

Memory 在 LLM prompt 里应该像这样出现：

- Allen wants concise voice and detailed document output.
- For Jarvis project, commits are more authoritative than stale docs.
- A worker's report is the worker's; say so when relaying it.

不要塞"All observations from last 30 days..."。详见 §10 Situation Packet Block 6 Memory / Profile Hints。

9.8 Memory 的权威等级

Memory 永远低于 fresh evidence。权威顺序：

current user instruction
  > runtime policy / invariants
  > fresh tool / state evidence
  > Obsidian canonical docs
  > Memory
  > general knowledge

具体：

  • Memory 不能覆盖当前 Allen 明确说的话
  • Memory 不能覆盖 fresh tool state
  • Memory 不能突破 invariant

9.9 冲突和更新

Memory 必须支持 supersede，而不是简单删除。

Old memory:
  Allen prefers daily summary reminders.

New observation:
  Allen finds unsolicited daily summaries annoying during coding.

Result (old memory superseded or narrowed):
  Daily summary reminders are acceptable only when explicitly
  requested or during wrap-up.

这比"删掉旧记忆"更可审计。

9.11 最危险的三类记忆

1. Mood inference. "Allen 看起来累了"、"Allen 不开心"——如果没有明确表达，不要长期写。
2. Unverified work state. "某任务完成了"——如果只是 agent 说的，不要写成事实（参见 §13 I8, I10）。
3. Over-generalized preference. 一次反馈不能变成永久偏好。"今天别提醒我"不能写成"Allen 不喜欢提醒"，只能写成"Allen suppressed reminders during this Focus session"。等重复出现后再提升为长期偏好。

Memory Boundary: Memory stores stable, reusable personal knowledge that reduces Allen's future explanation burden. It is a derived projection from events, evidence, tasks, feedback, and canonical notes. It must not store current mutable state, raw logs, raw sensor data, task status, unverified claims, secrets, or full transcripts. 10. Situation Packet

第一原则：Situation Packet 不是 State Object 的摘要，而是本轮决策所需的最小可证据化上下文。

不是"把 Jarvis 知道的都压缩给 LLM"，而是"这轮要正确行动，LLM 最少需要知道什么"。

10.1 边界

State Object projections  ──→  Runtime Decision assembler  ──→  Situation Packet  ──→  LLM

左边可以无限大；右边是 token-bounded 决策接口。Runtime Decision assembler 负责装配，LLM 不能自己编——packet 不够时 LLM 必须调 tool 或 ask，不能假设。

12. Attention Policy

第一原则：Attention Policy 不负责自动切 mode；它只负责对具体事件选择处理通道。

它不回答："Allen 现在是什么模式？"它回答："这个事件现在应该静默记录、排队、显示、提醒、询问、执行，还是打断？"

12.1 为什么它重要

Jarvis 会越来越多地观察世界：agent reported complete · tests failed · task blocked · 时间到了 · 灯没关 · Allen 坐到桌前 · Allen 离开房间 · commit hook 发现风险 · Codex 卡住 · sensor 状态变化 · Allen 连续忽略某类提醒...

如果每个事件都说出来，Jarvis 会烦。如果什么都不说，Jarvis 没用。Attention Policy 就是中间层。

12.2 核心架构

event  ──→  subscriber  ──→  candidate intervention  ──→  attention policy  ──→  channel decision

不是全局 polling，不是自动切 mode——它是 per-event 的通道选择器。

每个 candidate intervention 至少携带：

  • event_type
  • candidate_action
  • subject
  • confidence
  • urgency
  • relevance
  • risk
  • reversibility
  • expiry
  • current_mode
  • active_task_id
  • current_surface
  • interruption_cost
  • annoyance_history
  • user_feedback

这些不全是 0-1 分数。很多应该是 enum。

if mode Rest                          -> suppress work events

Channel scoring（剩下候选）

value = urgency + relevance + expiry + expected_helpfulness
cost  = interruption_cost + annoyance_penalty + uncertainty + risk

但不要暴露成用户配置。

Feedback adjustment（每次主动行为后记录）

  • accepted
  • ignored
  • dismissed
  • corrected
  • annoyed
  • useful

同类事件下次自动调整通道。

12.9 一句定稿

13. Invariant Gate

第一原则：Invariant Gate 是 Jarvis 的非协商 runtime 边界。LLM、agent、prompt、mode、tool 都不能绕过它。

它不是 prompt 风格的提醒，也不是 LLM 应该"小心"的建议。它必须由 runtime 强制。任何未来能力升级，invariant 保持不变。

13.1 三段 Gate（应用位置）

Gate触发时机主要检查
Pre-action Gateaction.authorized 之前policy 是否允许 · caller 是否有 tool_surface 权限 · entity / write target 是否可信 · 是否需要 confirmation · workdir 是否在 scope · 外部副作用 risk
Post-action GateTool 返回，写 action.result_observed 之前结果 cap（3.5.11） · artifact spill · 不解释、不判定（ADR 0019）
Pre-emit GateLLM 要输出给 Allen 之前routine plan · pending-confirmation 模板行 · correction prefix（3.4.12）

13.2 Invariants

I1. No State Without Event. 任何持久状态变化必须来自 event。
I2. Event Is Immutable. 已写入 event 不可修改，只能 append correction / supersede event。
I3. Projection Is Read-Only. Projection 只能由 event rebuild / update，不能被 LLM / tool 直接改。
I4. No Action Without Effective Policy. 任何 action 必须绑定当前 effective_policy。
I5. Tool Surface Is Enforced. Caller 只能调用当前 policy 暴露的工具（参见 §14 Tool Surface）。
I6. Entity ID Cannot Be Invented. 设备、文件、task、agent、窗口等真实对象 ID 必须来自 trusted source 或 resolver。
I7. High-Risk Action Requires Confirmation. 删除、发送、push、merge、rebase、kill、install、secret / config / system 改动必须确认。
I8–I11（retired，ADR 0019）. agent report ≠ verification、execution ≠ postcondition、claim ≤ evidence、worker cannot self-verify 这四条随审核链退役：Jarvis 不再对 worker 的结果做判定，worker 的最终消息原样转述（§15）。编号保留。
I12. Memory Is Not Current State. 长期 memory 不能证明当前 mutable state；当前状态必须来自 fresh tool / state evidence。

13.3 跟 Mode 的关系

Mode 可以降低或提高默认权限，但不能突破 invariant：

  • Collaborate 可以允许 delegate worker，但不能绕过 confirmation gate
  • Rest 可以允许关灯，但不能允许未解析 entity_id 就控制设备
mode / policy  ──→  changes defaults
invariant      ──→  defines hard limits

13.4 跟 Prompt 的关系

Prompt 可以告诉 LLM 规则，但 runtime 必须强制。Prompt 说"要确认"不够——high-risk action 的 confirmation 和 write target 的解析由 runtime gate 保证，不靠 prompt。

13.5 一句定稿

Invariant Gate is Jarvis's non-negotiable runtime boundary. It enforces pre-action permission, entity and confirmation checks. Modes and prompts may change behavior, but they cannot override invariants: no state without event, no invented entity IDs, no high-risk action without confirmation, and no memory as current state. What a worker reports is relayed, not judged (ADR 0019).
Invariant Gate 是 Jarvis 的非协商 runtime 边界。它在行动前检查权限、风险和实体。Mode 和 prompt 可以改变行为偏好，但不能覆盖 invariant：无 event 不改 state，不伪造 entity_id，高风险动作必须确认，memory 不是当前状态。Worker 报告什么就转述什么，不做判定（ADR 0019）。

15. Codex Integration

第一原则（ADR 0019）：Jarvis 不判定 worker 做了什么。Worker 是 Codex app-server 上的一个 thread；Allen 自己的桌面 Codex 会话通过 hooks 被观察，从不被接管。本节替代原 Agent Protocol，锚点保留。

15.1 Worker = Codex app-server thread

  • daemon 起一个常驻 codex app-server（unix socket，L4 codex_app_server.py）；stop 终止整个进程组，node 包装进程和原生二进制一起退出。CLI 版本是 pinned 外部依赖。
  • 四个 flat tools：spawn_worker（立即返回 worker_id）、wait_worker（阻塞到终态，action.result_observed 携带 final_message）、send_input、close_worker。每次调用各走一条完整 action 链（§3.5.9）；没有 worker.* 事件。
  • Worker 的最终消息是 untyped string，原样进入下一轮 tool-result message：不解析、不评分、不生成 claim。
  • Worker 的 approval request 原样转出；被拒绝后 worker 自行结束。

15.2 Hooks：观察 Allen 的桌面 Codex 会话

会话卡片的展开与操作按钮显隐独立：自动展开时文字占满内容宽度，左上移除按钮及右侧回复／打断按钮仅在悬停或键盘聚焦交互时浮现。右侧按钮绝对定位覆盖文字区域，通过文字尾部渐隐让出视觉空间，不改变文字宽度或重新排版；移开恢复全宽文字，不因此收起尚待交互的活动卡片。

Dashboard 缩略模块展开为详情时保留原卡片，在原窗口中连续改变位置和尺寸，返回时反向收回。摘要与详情的交接跟随卡片尺寸进度，不出现内容全空的中间帧；已显示面板因内部内容变化而调整高度时，不重播整块内容的入场淡入。

  • ~/.codex/hooks.json 对 SessionStart / UserPromptSubmit / PermissionRequest / PostToolUse / Stop / SessionEnd 各挂一个 command handler：scripts/codex_hook_log.py（安装副本 ~/.jarvis/codex-hooks/log_hook.py，路径独立于任何 worktree）。
  • Handler 契约：payload 从 stdin 读；追加一行 {ts, event} 到 ~/.jarvis/codex-hooks/<Event>.jsonl；POST 同一 payload 到 /inherent/codex-hook（JARVIS_INHERENT_BRIDGE_PORT，默认 8006）；stdout 永远为空——空输出即"不做决定"，Codex 按默认继续。daemon 不在时静默，jsonl 仍是记录。
  • Codex 只运行 [hooks.state] 里有 trusted_hash 的 handler；hooks.json 每次修改后必须重新 trust（app-server hooks/list → config/batchWrite），否则静默跳过。
  • L5 把 payload 折成每个 session 一行（jarvis/surface/codex_sessions.py）：SessionStart → idle，UserPromptSubmit → running 并记录 turn_started_ms，PermissionRequest → needs_input，PostToolUse → running，Stop → finished（带 last_assistant_message），SessionEnd 保留近期记录并将未完成状态转为 idle。内存态，daemon 重启即清空；非活动记录按最近活动时间保留 24 小时，running / needs_input 不受数量限制。GET /inherent/codex-sessions 最新在前；Resonance 在上次请求结束后间隔 2 s 轮询，断线或失去观测时不把缓存活动状态当作实时状态。
  • Resonance Codex 详情为固定高度的紧凑滚动区域，普通行 32px、展开胶囊 64px，不显示服务商图标、顶部说明和底部操作提示。相邻收起行之间显示淡分隔线，展开卡片周围隐藏分隔线。运行中、需要输入、完成尚未交互的任务自动展开；点击底座成功请求打开原会话或打开回复框，记录本轮状态已交互，退出 Hover／回复后收起；新轮次、新待处理请求或新完成状态重新展开，普通进度更新不重置。该交互标记仅控制展示，不表示原任务已完成或授权已处理。Hover 也可展开两行胶囊并推开邻行；左上小 × 仅移除 Jarvis 中本轮记录（可撤销），下一轮重新出现；长按 1 s 固定／取消固定，移动或滚动取消手势，固定记录免于 24 h 过期。近期快照、固定、交互和本轮移除标记存于本地 UI 存储。优先用 Codex 本地 session_index.jsonl 中的名称作为标题，未取得时回退到观察到的用户请求。点击底座通过 codex://threads/{thread_id} 请求系统打开原会话；系统接收链接不等于确认会话已读。回复按钮仅展开胶囊内输入框，输入时保持展开，Esc 收回并保留本次面板内草稿；外部桌面会话暂不支持直接回复／打断，输入框提示发送未接通，打断按钮明确标记不可用，不通过 worker app-server 操作它们（ADR 0022）。

18.2 Voice

最高打扰成本 surface。只承载：

  • 结论 / 状态 / 一句确认
  • 必要问题
  • 高价值提醒
  • 低复杂度环境 / 日常反馈

不适合：长日志 · 多路径 · 文件列表 · diff · 测试输出 · 长计划 · 复杂证据 · 多个任务状态。

规则： Speak only what Allen needs to hear now. Put durable detail elsewhere.

例："Codex 报告完成了，我已经放到待审核里，还没验证。"——而不是把所有文件和测试读出来。

18.3 Inherent Panel

工作时最重要的视觉 surface。适合：

  • 当前 active task
  • agent status
  • evidence summary
  • diff / test 摘要
  • next action
  • clipboard / image attach preview
  • command result
  • confirmation prompt
  • short checklist
  • mode / state pill
  • 对话记录：memory.db records 自 session.history_since 起的行，与后台请求的历史同源（§10.5.1），经 GET /inherent/conversation?after=<seq> 增量拉取；文字模式默认展开；后台正在流式输出的回答作为末行显示，落库后由记录行接替；Live 会话进行中，该会话已落库的行让位给实时字幕，不重复显示

它是 voice 的搭档：

voice  =  conclusion
panel  =  evidence and action controls

work cockpit 里，Inherent Panel 应该是主实时 UI。

18.4 Mac Notification

打扰成本高于 Panel，低于 Voice。适合：

  • 非语音场景下的中高重要提醒
  • long-running agent 完成
  • timer / deadline
  • task needs review
  • system health problem

不适合：普通状态变化 · 低价值建议 · every agent log · 可等下次交互的东西。

Notification 必须 rate limit。

18.5 Dashboard / Cockpit

低打扰、可浏览的状态面。适合：

  • Codex sessions（running / needs_input / finished，§15.2）
  • 当前工作状态（§3.3.5a，ADR 0023）：GET /inherent/work-state 每 60 s 轮询只读，刷新按钮 POST /inherent/work-state/refresh 与对话里的 refresh_work_state 走同一条分析；显示上次结果、数据时间、分析时间，更新中保留旧结果，失败标"未更新"，较旧的返回不覆盖较新的记录
  • pending review
  • evidence status
  • current project state
  • blocked tasks
  • queue
  • mode / history
  • recent events

Resonance 桌面首页由胶囊中的 Dashboard 按钮展开／收起，不另设通知入口或顶部最小化按钮。通知复用原有卡片，位于首页四模块下方；通知取消叠层，固定区域最多容纳两条完整卡片，其他事项通过区域内滚动查看，无待办通知时不保留通知区域，窗口高度随内容平滑收起。额度摘要在同一行显示重置倒计时、使用进度和百分比；所有模块展开页移除顶部标题和返回箭头，使用底部主色短条点击或向下拖动返回首页；拖动仅从短条触发，不占用列表滚动或胶囊拖动手势。额度详情默认采用 B2 紧凑折叠视图，三个分区独立展开／收起，初始仅订阅额度展开，仍可在设置切换其他布局。Codex 订阅标题显示 Codex Pro，倍率标签显示 5X。首页卡片到详情的边框与尺寸、Dashboard 以约 200ms 整体淡入并从上方 6px 滑入，不做卷帘式裁切；通知引起的高度变化保持连续过渡；分区与标签切换保留轻量动画。胶囊、Dashboard 与 transcript 入口光缝共用外观主色和玻璃设置。光缝在中部 Live 与下方光缝组成的完整矩形区域悬停时显示，移出后隐藏。Resonance 的 macOS 桌面浮窗采用非激活 panel 与 floating 层级，配置为加入普通桌面及其他应用的全屏 Space，在显示和焦点切换后维持置顶，置顶操作不夺取其他应用的键盘焦点。

Resonance 的文字输入在顶部胶囊下方打开，保持 Live 控件及其状态不变。文字输入、完整对话记录和 Dashboard 是同一浮窗内可组合的区域，初始依次排列；各自支持关闭、折叠和抓住标题栏拖动排序；拖动时保留占位并让相邻模块平滑让位，Escape 可取消，Alt 加上下方向键提供键盘排序。折叠使用独立箭头，拖动不触发折叠，切换或折叠不丢弃草稿。展开区默认使用 Dashboard 风格的中性黑色玻璃、灰白文字和边框，保留现有主题强调色；墨绿色处理保存为可复用预设。模块内容在尺寸就绪后渐入位移，退场完成后再释放高度；快速反向保留当前几何和速度，融合容器及原生玻璃随尺寸连续更新。减少动态效果时直接切换到最终状态，内容超过屏幕可用高度时在展开区内滚动。输入区下方左侧的附件按钮目前禁用，仅作占位，右侧发送保留真实文字链路。中央光缝触发区高度为原来的约 60%，释放的高度归还 Live 区域，总胶囊高度不变。

Dashboard 不是 chat。它是"我现在有哪些事"的地图。

当 Allen 问"我现在还有什么没收尾？"——Jarvis 可以 voice 给一句总结，dashboard 展示全量。

18.6 Obsidian / Document

长期人类可读知识库。适合：

  • session note
  • research note
  • product constitution
  • architecture decision
  • handoff
  • postmortem
  • weekly summary
  • decision record

不适合：raw event log · current task state · transient notifications · sensor state · every tool result。

Obsidian 保存"值得以后读"的东西，不是 runtime 状态。

18.7 OLED / Room Display

Ambient low-bandwidth surface。适合：

  • 当前 mode
  • timer
  • active task 简短名
  • agent running / needs review indicator
  • room state
  • muted / listening / standby
  • simple icons / status

不适合：长文本 · evidence · logs · 多任务列表 · 复杂选择。

价值是低打扰存在感。

18.8 Environment Action

Hue、音量、灯光、屏幕亮度也是 surface——它们不是信息文本，但表达状态。

适合：

  • 进入 Focus / Collaborate 的灯光场景
  • Rest / Night 的暖光低亮
  • agent running 的轻微 status indicator（谨慎）
  • 勿扰 / 静音反馈
原则： Environment should support state, not announce everything.

18.9 Agent / Worker Handoff（特殊出口）

给 worker 的 surface，不是给 Allen。适合：

  • task context package
  • scope
  • acceptance claims
  • constraints
  • evidence so far
  • output contract

详见 §15 Agent Protocol。"输出给 agent"的质量直接决定 agent 是否跑偏，所以也是 Surface Design 的一部分。

18.12 7 条硬规则

1. Voice never carries dense evidence. 证据放 panel / document。
2. Panel is the default work surface. 工作状态优先 panel，不优先 voice。
3. Obsidian is for durable knowledge, not runtime state.
4. Notifications are rate-limited. 只用于 time-sensitive 或 review-worthy 事件。
5. OLED / display is ambient state only.
6. Environment actions should be reversible and low-noise.
7. Every surface emission should trace back to an event or decision.

18.13 一句定稿

Surface Design assigns each Jarvis output to the lowest-interruption surface that can still support the required action. Voice carries immediate conclusions, questions, and urgent low-complexity notices. Inherent Panel carries work evidence, task state, and controls. Dashboard carries persistent operational state. Obsidian carries durable human-readable knowledge. OLED and environment surfaces carry ambient state. Mac notifications are rate-limited exceptions, not the default.
Surface Design 负责把 Jarvis 的输出放到打扰成本最低且足够可操作的出口。Voice 只承载即时结论、必要问题和低复杂度紧急提醒；Inherent Panel 承载工作证据、任务状态和操作控件；Dashboard 承载持久 operational state；Obsidian 承载长期人类可读知识；OLED 和环境动作承载 ambient state；Mac notification 是受限例外，不是默认出口。
