# Goal: gated-action-cancel

## Goal
An utterance asking to cancel a running action resolves to that exact action and cancels it through `ActionRunner.cancel_action`, admitted by a `pre_action_gate` arm that proves the request names the same gate event that admitted the target — with no confirmation question, no lease, and `ResponseInterruptPolicy.action_action` still `Literal["never"]`.

## Why
ADR-0008 D10 (docs/adr/0008-real-time-response-streaming.md:571-729) specifies the whole action-cancellation protocol and none of it exists: `resolve_cancellable_action`, `CancelActionRequest` and `dispatch_authorized_action_cancel` appear only as ADR prose (0008 :594-609, :639, :682, :718; 0014 :1477). The L4 half is built and unreachable — `ActionRunner.cancel_action` (jarvis/execution/action_runner.py:1069) has no caller outside the class and its own tests, so a spawned Codex worker can only be stopped by killing the daemon.

## Current behavior
- Base: `realtime-integration` at `199036c` (lane A owns the runtime hotspots).
- `ActionRunner.cancel_action` (jarvis/execution/action_runner.py:1069) is called from exactly two places in production code — `ActionHandle.cancel` (:661) and `shutdown` (:1374) — plus tests/integration/test_wave5_background_actions.py:588/:712/:722/:732 and tests/scenarios/test_live_wave5_realtime.py:665. Nothing in L3 or the runtime reaches it.
- It returns `CancelUnsupported` immediately when `cancellation_mode == "unsupported"` (:1077-1078). That is the default on every `ToolDefinition` (jarvis/execution/tools.py:544) and `spawn_worker` is the only tool declaring otherwise: `is_async=True` (:5789), `cancellation_mode="terminate_process"` (:5810), `domain="agent_control"` (:5792). `spawn_worker` is today's entire cancellable universe.
- **A dispatched-but-not-yet-running action cannot be cancelled.** `cancel_action` looks up `self.context_of(action_id)` (:1080) and the context is only created after `action.running` is emitted, built from that row's uid (:868-879). With no context it returns `CancelUnconfirmed(reason="no_live_context")` (`_answer_without_context` :1122-1143) and writes no terminal; the action then runs normally. `_answer_without_context` returns `CancelAlreadyTerminal` instead when the durable fold already holds a canonical terminal.
- `action.cancelled` is written only after confirmed quiescence, with `source_event_id = context.running_event_uid` (:1087-1103). Its payload carries `action_id`, `reason`, `cancellation_mode`, `requested_by_turn_id`; `stash_ref`, `run_id` and `task_id` are stamped **only when `context.stash_ref is not None`** (:1094-1096 via `_stamp_worker_identity` :516-532). A cancelled action that never stashed carries no `run_id`.
- Registry payload shapes (jarvis/state/event_log.py): `gate.evaluated` required `("gate", "outcome", "reasons")`, optional includes `action_id`, `lease_id`, `authorization_id`, `dispatch_id` (:316-352); `action.dispatched` required `("action_id",)`, optional `("result_expected_by_ms",)` (:363-374); `action.running` required `("action_id",)`, optional `("resource_keys", "resource_mode")` (:376-388) — **no `run_id`**; `action.cancelled` required `("action_id",)`, optional `error/reason/requested_by_turn_id/cancel_scope/cancellation_mode/stash_ref/run_id/task_id` (:428-449); `run.started` required `("run_id", "task_id")`, optional `("runner",)` (:482-488).
- **`action.dispatched` does not reliably carry its admitting gate.** The ordinary dispatch path emits it with payload and correlation only, no `source_event_id` (jarvis/execution/tools.py:4886-4892). Only the confirmation-backed outbox path sets `source_event_id=dispatch.gate_event.event_uid` (jarvis/state/authorized_dispatch_outbox.py:233-236, whose integrity checks at authorization_snapshot.py:238-249 depend on it). The path-independent record is `gate.evaluated` itself: every pre-action verdict is emitted with `payload["action_id"]` and `source_event_id=<the action.proposed uid>` (jarvis/decision/__init__.py:1898-1910).
- `run.started` is emitted inside `spawn_worker_handler` with `source_event_id=<that action's action.running uid>` and the action's correlation (jarvis/execution/tools.py:1040-1046) — that is the only join from an action to its `run_id`.
- `EntityRegistry` folds four routes and no more (jarvis/state/projections.py:1165-1245): config `file:` bookmarks, `task:` from the Task Ledger, `repo:` from `repo.state_observed`, `file:` from `entity.resolved`. There is no `action:` kind. `EntityRegistryEntry` has seven fixed fields and no run slot (:1016-1042); its docstring calls `entity_type` an open enum of `file|repo|task` (:1020-1023).
- `StatusBoard.open_actions` (projections.py:847-882, fold :968-1010) already tracks non-terminal actions, opened by `action.dispatched` and closed by `_STATUS_BOARD_TERMINAL_ACTION_TYPES = {action.result_observed, action.failed, action.timeout_assumed, action.cancelled}` (:770-777). It is on the packet (jarvis/decision/packet.py:93, :155) and already rendered to the LLM (jarvis/decision/__init__.py:973-977). It carries `action_id` + `dispatched_ts_ms` only.
- `pre_action_gate` (jarvis/decision/gates.py:242-250) takes `tool_def`, `entity_registry`, `pending_confirmations`. Check 2 trusts a target when `action_request.target_entity_ref in entity_registry` — plain membership by `entity_id` string (`_check_entity_trusted` :216-234). Check 4's `needs_lease` is `risk_rank(action_request.risk_level) >= risk_rank(policy.confirmation_threshold)` (:410-412); `effective_policy` pins `autonomy_ceiling="L3"` and `confirmation_threshold="L3"` (jarvis/decision/policy.py:225-226), so an **L2 request needs no lease and the gate never asks** — which is exactly what D10 :683-684 intends.
- `validate_requires_confirmation` (policy.py:328-358) fails boot unless `requires_confirmation == (risk_rank(risk_level) >= risk_rank(threshold))`, so an L2 tool must declare `requires_confirmation=False`.
- No `cancel_action` `ToolDefinition` exists. `ToolDefinition` is at jarvis/execution/tools.py:474-547, `ToolRegistry.register` at :4666, `for_caller` (which builds the LLM's tool list) at :4684-4694, and `build_default_registry` (:5697) already receives the live `ActionRunner` and passes it to the registry (:5771-5778); the runtime hands it in at jarvis/runtime/__init__.py:1350-1372.
- `default_resource_key_resolver` (tools.py:5183-5218): `spawn_worker` takes `realpath(repo)` `write_exclusive`; `verify_diff` borrows its parent's scope; a `read_only` tool gets `resource_keys=()`; **anything else that mutates falls to `GLOBAL_RESOURCE_KEY` / `global_exclusive`**.
- `ResponseInterruptPolicy.action_action` is `Literal["never"]` (jarvis/shared/realtime.py:183-198) and its docstring states the type is the enforcement.
- An ordinary answer already routes to `voice_notify` (gates.py:945, ADR-0009 D4's 2026-09-05 amendment, docs/goals/speak-ordinary-answers.md), and `ask_confirm` already sits outside the ADR-0009 D4 TTS suppression set (jarvis/decision/__init__.py:3124-3128) — nothing in this card needs to change how an answer is spoken.
- `realtime.actions.action_runner` and `.true_async_workers` are both `false` in config/jarvis.yaml; without the runner, `dispatch` runs handlers inline and there is no background action to cancel.

## Target behavior
- **L2 — `action:` entity kind.** `_fold_entity_registry` gains a fifth route per ADR-0008 D10 (:625-634): `action.dispatched` — the first durable action event, the same opener `StatusBoard.open_actions` uses — registers `EntityRegistryEntry(entity_id="action:<A>", entity_type="action", canonical=A, aliases=(), confidence="exact", source_event_id=<that row's uid>, last_seen_ms=<its ts>)`. Any member of `_STATUS_BOARD_TERMINAL_ACTION_TYPES` evicts it. The registry's `action:` universe is therefore exactly the non-terminal set, and the gate's existing entity check refuses a terminated id with no new gate arm.
- **L2 — the admission lookup.** The same fold pass produces `action_id → {dispatched_event_uid, admission_gate_uid, lease_id?, run_id?}`, added as one field on `ProjectionSet`:
  - `admission_gate_uid` is the `event_uid` of the last `gate.evaluated` row with `payload["gate"] == "pre_action"`, `payload["outcome"] == "pass"` and `payload["action_id"] == A`. This is read from `gate.evaluated` rather than from `action.dispatched.source_event_id` because the ordinary dispatch path sets no `source_event_id` (tools.py:4886-4892); `lease_id` rides along when that row carries one, covering D10's leased case.
  - `dispatched_event_uid` is the `action.dispatched` row's uid.
  - `run_id` is joined **only** from `run.started`, matched to the action by that row's `source_event_id` (the action's `action.running` uid) or its correlation `action_id`. `action.running` carries no `run_id` and is never used for it.
- **L3 — resolution.** `resolve_cancellable_action(packet)` returns one of three results: `resolved` with an `ActionRef("action:<id>")` when exactly one non-terminal action exists (or when a qualified request names exactly one); `ambiguous(candidates)` when more than one is non-terminal; `none` when none is. The LLM's raw `target_action_id` string is never trusted alone — it is accepted only when it names a current `action:` entry.
  - `ambiguous` → an ordinary clarifying answer naming the candidates ("哪一个？…"), on the existing `voice_notify` default. It is a question, not a confirmation: no `confirmation.requested`, no pending slot, no lease. Allen's reply is a new turn that resolves to one candidate.
  - `none` → an ordinary spoken answer, no tool call, no `action.proposed`, no `gate.evaluated`.
- **L3 — the request.** `CancelActionRequest` takes ADR-0008 D10's shape (:594-609): `request_id`, `target_action_id`, `caller_principal`, `risk_level`, `reason`, `requested_by_turn_id`, `source_event_uid`, `authorization_gate_event_uid`, `authorization_lease?`. The resolver fills `authorization_gate_event_uid` from the L2 admission lookup for that target, so a well-formed request always matches and a mismatch can only come from a forged or stale one.
- **L3 — the gate arm.** `pre_action_gate` gains one keyword-only projection input (the admission lookup, same shape as `entity_registry`/`pending_confirmations`) and one check that runs only for a `cancel_action` request: the request's `authorization_gate_event_uid` must equal the lookup's `admission_gate_uid` for `target_action_id`. Absent, unknown, or mismatched → `refuse`, never `confirm_required` (Allen re-granting cannot fix a stale uid). Checks 1-3 are unchanged and check 4 is inert at L2. This one arm is the single truth source for the match; nothing downstream re-checks it.
- **L4 — the tool.** A `cancel_action` `ToolDefinition` exactly as ADR-0008 D10 writes it (:655-681): `risk_level="L2"`, `requires_confirmation=False` (which `validate_requires_confirmation` requires at L2 under the L3 threshold), `allowed_callers={JARVIS_LLM}`, `result_semantics="ack"`, `is_async=False`, `input_schema` `{target_action_id, reason}` with `additionalProperties: false`, `domain="agent_control"` (already a spec §14.1 value, docs/spec.html:2606), `read_only=False`, `requires_entity=True`, `post_action_check=None`, `result_budget_s=None`. It is registered inside `build_default_registry` only when an `ActionRunner` was supplied, so with `realtime.actions.action_runner` off (its default) the registry, the LLM's tool list and every event trail are byte-identical to today and no new config key is added.
- The handler closes over the runner and calls `ActionRunner.cancel_action(target_action_id, reason=..., timeout_s=<the runner's cancel budget>, cancellation_mode=<the target's own declared mode, read from its live context>)`, then serializes the returned `CancelOutcome` — `CancelAccepted` / `CancelAlreadyTerminal` / `CancelUnconfirmed` / `CancelUnsupported` — as the ack. It writes no event of its own; `action.cancelled` stays the runner's, written only after confirmed quiescence.
- A `CancelUnconfirmed(reason="no_live_context")` — the dispatched-but-not-yet-running case — is reported to Allen as "还没真正开始，没能停下", not as a success. The registry lists the action because it is non-terminal and its gate uid is real; whether it can be stopped *right now* is the runner's current-state check, exactly the D10 split between durable provenance and current cancellability (:639-641).
- `cancel_action` gets an explicit branch in `default_resource_key_resolver` returning `resource_keys=(), mode="read_shared"`. It signals a handle and mutates no resource; taking the target's key — in any mode — would queue the cancel behind the very `write_exclusive` lease it is trying to release.
- `ResponseInterruptPolicy` is untouched: cancelling a response still never cancels an action, and cancelling an action never touches a response run.

## Boundaries and non-goals
- Layers that may change: L2 (`projections.py`), L3 (`gates.py`, `decision/__init__.py`, `packet.py`), L4 (`tools.py`), runtime. No config key.
- Must not change: `ResponseInterruptPolicy` (jarvis/shared/realtime.py:183-198); `ActionRunner.cancel_action` and the terminal-arbitration/quiescence rules in jarvis/execution/action_runner.py; the ADR-0012 confirmation flow — no `confirmation.requested`, no pending slot, no lease minted, `_stage_and_request_confirmation` and `_handle_confirmation_accepted` untouched; `EntityRegistryEntry`'s field list; `StatusBoard`; `effective_policy`'s thresholds; any `desktop/` Swift source.
- Non-goals: barge-in, the `InterruptUtteranceRouter` and the stop-phrase grammar (lane B's card); `dispatch_authorized_action_cancel` as a separate runtime entry point (the ordinary gated dispatch of the registered tool is the shipped mechanism); making any tool other than `spawn_worker` cancellable; cancelling a queued action before it runs; response cancellation of any kind.

## Rejected approaches
- Routing the cancel through ADR-0012's ask/answer path — D10 :683-684 fixes the risk at L2 precisely so an explicit cancel utterance does not trigger a redundant second question, and at `confirmation_threshold="L3"` an L2 request produces no `confirm_required` anyway (gates.py:410-412). Confirming would also require a second lease-minting site, which gates.py:600-630 records as a non-goal.
- Reading `admission_gate_uid` from `action.dispatched.source_event_id` — set only on the confirmation-backed outbox path (authorized_dispatch_outbox.py:233-236); the ordinary path leaves it unset (tools.py:4886-4892), so every unleased action would fail the match.
- Reusing `StatusBoard.open_actions` as the gate's trusted universe — check 2 matches only the Task Ledger and the `EntityRegistry` (gates.py:224-228); a status-board id would refuse. The board stays untouched and keeps informing the LLM.
- Putting `run_id` on `action.running` so one row answers everything — the registry says it carries none (event_log.py:376-388) and `run.started` is where it is minted (:482-488); widening the earlier event would make the dispatcher claim an id that does not exist yet.
- Checking the gate uid in the handler or the runtime instead of the gate — D10 :682 requires the admission decision to be the gate's; a second checker is a second policy.
- Giving `cancel_action` the target's resource key — it would block behind the target's `write_exclusive` lease.
