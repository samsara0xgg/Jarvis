# Goal: cancel-request-on-the-wire

## Goal
The durable `CancelRequestView` that the L2 fold already builds and checkpoints reaches the `action.upsert` wire and the Swift client's `ActionViewState`, and the client has one settled rule for which of its two cancel notions wins.

## Why
D13's cancel trail exists end to end in Python except for the last hop: it is folded, checkpointed, and then dropped at the presenter. A client that reconnects therefore cannot tell an accepted-but-not-terminal cancel from no cancel at all, which is exactly the case D13 introduced the separate view to survive (docs/adr/0014-inherent-realtime-ux.md:977-980). Everything needed already exists; only a wire key, a Swift slot, and a precedence rule are missing.

## Current behavior
- `CancelRequestView` is folded and checkpointed with six fields — `request_id`, `target_action_id`, `state: CancelRequestState`, `revision_cursor`, `proposed_event_uid`, `reason_code | None` (jarvis/state/inherent_view.py:262-279) — and hangs off `ActionView.cancel_request` (:305). Its own docstring records that it is "folded and checkpointed but never serialized" (:268-269).
- `CancelRequestState` is `received | authorized | quiescing | rejected | failed | resolved` (jarvis/state/inherent_view.py:134-136).
- `action_item` emits eight keys and deliberately omits `cancel_request` (jarvis/surface/inherent_presenter.py:111-129, the omission stated in its docstring at :114-118); `_change_payload` adds `"kind"` for nine on the wire (:171).
- Swift `ActionUpsert` has nine properties and no cancel field (desktop/inherent-swift/InherentRealtime/RealtimeViewDTOs.swift:259-281). `viewState(of: ActionUpsert)` maps all nine (RealtimeReducer.swift:559-571).
- Swift already carries a second, client-only cancel notion: `ActionCommandOverlay { none, cancelSubmitting, cancelRequested, cancelRejected }` (RealtimeState.swift:317-322), stored as `ActionViewState.commandOverlay` (:334). `applyAction` deliberately preserves it across a canonical upsert — "The command overlay and the progress hint are local and ephemeral truth; a canonical upsert never carries them and never erases them" (RealtimeReducer.swift:598-601).
- That overlay has **no producer today**: across all of `desktop/`, `commandOverlay` appears only as its declaration, its `.none` default, and the preservation line (RealtimeState.swift:317,334,347,359; RealtimeReducer.swift:600). The collision this card settles is therefore latent, not yet observable in a running client. `progressHint` on the same lines *does* have a producer (RealtimeReducer.swift:751) and is not this card's business.
- Two existing Python tests pin today's absence: `ACTION_WIRE_KEYS` (tests/integration/test_inherent_action_view.py:46-56, asserted as an exact set at :265 and :691) and `assert "cancel_request" not in cancelled[0]` (:425). Both must flip.
- The Swift DTO fixture that must grow: `test_viewDeltaDecodesEveryDurableMutation` (desktop/inherent-swift/InherentCardTests/Realtime/RealtimeViewDTOTests.swift:14), whose `action.upsert` entry is at :33-36 and whose assertions are at :94-100. That file uses inline JSON, not golden fixtures, by its own recorded exception (:4-6).

## Target behavior

- `action_item` emits a tenth key `cancel_request`: `null` when the action has no request, otherwise a nested object carrying D13's four named fields — `request_id`, `state`, `revision_cursor`, `reason_code` (docs/adr/0014-inherent-realtime-ux.md:936-940). The key is always present, matching the presenter's existing habit of spelling absent optionals as `null` (`response_group_id`, `task_id`, `target` at inherent_presenter.py:120-125), so the wire key set stays fixed and the exact-set assertions at test_inherent_action_view.py:265,691 stay exact-set assertions.
- `target_action_id` and `proposed_event_uid` do not reach the wire. The first is redundant with the enclosing item's `action_id`; the second is fold-internal provenance with no client that could join on it. If the session finds a real consumer for either, it stops and reports rather than adding it.
- Swift gains a nested `Decodable` struct mirroring those four keys, an optional `cancelRequest` property on `ActionUpsert` with a spelled-out `CodingKeys` entry (the file's rule, RealtimeViewDTOs.swift:5-7), matching storage on `ActionViewState`, and the mapping in `viewState(of: ActionUpsert)`. The property is optional, so both a missing key and an explicit `null` decode to `nil`.
- The fold is unchanged. This card adds no derivation, no policy, and no new `kind` string.

### The overlay precedence rule — this card's real work

Adding the field is plumbing. The work is that after this card the client holds **two** cancel notions for the same action: the durable `cancel_request` the server folded, and the local optimistic `ActionCommandOverlay` the user's own click sets. `applyAction` today preserves the overlay across every canonical upsert (RealtimeReducer.swift:598-601), and that is correct *only* because a canonical upsert carries no cancel truth. Once it does, blind preservation would let a stale `cancelSubmitting` sit on top of a durable `rejected`. The rule, which the card requires be implemented and pinned:

> **The durable value wins the moment it exists.** When an incoming `action.upsert` carries a non-null `cancel_request`, the reducer stores it and sets that action's `commandOverlay` to `.none`: the server has acknowledged the request, so the optimistic guess is retired. When the upsert carries no `cancel_request`, the existing preservation stands unchanged — the overlay is precisely the pre-acknowledgement state, and it survives until the server answers.

Consequences the card fixes as contract:

- The overlay is redefined from "local truth a canonical upsert never erases" to "local truth a canonical upsert erases exactly when it supersedes it". The comment at RealtimeReducer.swift:598-599 must be rewritten to say that; `progressHint` on :601 keeps the old unconditional preservation and must not change.
- Both directions are pinned by test: overlay preserved when the key is absent or null, overlay retired to `.none` when it is present. One test each; neither iterates the `CancelRequestState` enum.
- If the session finds a case where the durable value must *not* win, it stops and reports rather than inventing a precedence rule.

### Python and Swift may ship in either order

No version gate, no capability entry, no coordinated release. `PROTOCOL_VERSION = 2` and `VIEW_SCHEMA_VERSION = 1` stay as they are (jarvis/surface/inherent_protocol.py:34-35) and `RuntimeCapabilities` gains no entry (:149-165); it is a feature-flag set with no per-field granularity. The evidence is that this exact asymmetry already runs in production in the other direction: Swift declares `freshnessMs` (RealtimeViewDTOs.swift:268,279) and Python has never emitted the key (inherent_presenter.py:114-116), and the client reads its absence as fresh. Python ignores unknown fields by `extra="ignore"` (inherent_protocol.py:41, rationale at :16-17); Swift ignores unknown keys (RealtimeViewDTOs.swift:5-7); a missing or null key for an optional Swift property decodes to `nil`.

The one caveat that does **not** apply here: an unrecognized `kind` string inside a durable `view.delta` throws rather than being ignored (RealtimeViewDTOs.swift:380-388). This card adds an optional field to an existing `kind`, never a new `kind`, so it stays clear of that edge.

## Boundaries and non-goals
- Layers that may change: L5 (`inherent_presenter.py`), the Swift client, tests, the smoke script, and ADR-0014 prose. L2's fold logic does not change; L3 and L4 are untouched.
- Must not change: the fold's cancel-trail derivation; `freshness_ms` code anywhere; `progressHint` preservation (RealtimeReducer.swift:601); the confirmation item builder (`inherent_presenter.py:131-143`) and `CONFIRMATION_WIRE_KEYS`; the D11 flow-control lanes; `RECENT_TERMINAL_ACTION_LIMIT` (jarvis/state/inherent_view.py:117) and the bounded-fold behavior the just-merged card added; `PROTOCOL_VERSION` / `VIEW_SCHEMA_VERSION` / `RuntimeCapabilities`.
- Non-goals, with reasons:
  - **`progress_label` and `user_action_required`.** These have no producer anywhere in the fold — they do not appear in `jarvis/state/inherent_view.py` at all, and exist only in ADR prose (docs/adr/0014-inherent-realtime-ux.md:961-965, with the no-producer status recorded at :969-975). Shipping them would require first deciding what computes them and from what policy. That is a design question, and it belongs to its own later card. Do not bundle an unsettled design with settled plumbing.
  - Any new `kind` string on the durable mutation union.
  - Rendering the cancel state in SwiftUI. This card lands the value in `ActionViewState`; binding it to a view is a controls/UI card's job.
  - Adding a producer for `ActionCommandOverlay`. The overlay stays unproduced; this card only fixes what happens when it and a durable value meet.
  - `freshness_ms` behavior. Its D13 prose is amended as an erratum (see Docs to sync); no freshness code is touched.

## Rejected approaches
- Omitting the `cancel_request` key when there is no request (the `freshness_ms` pattern) — it makes the action item's key set vary per action and forces the two exact-set assertions at test_inherent_action_view.py:265,691 to grow conditionals. A constant `null` is the smaller diff and matches the three optionals the builder already spells out.
- Serializing all six `CancelRequestView` fields — `target_action_id` duplicates the enclosing `action_id` and `proposed_event_uid` is fold-internal provenance the client cannot use. D13's own block names exactly four.
- Bumping `VIEW_SCHEMA_VERSION` or adding a `RuntimeCapabilities` entry — see "Python and Swift may ship in either order"; the `freshnessMs` precedent already proves an additive optional key needs neither.
- Letting the local overlay keep winning after a durable value arrives — that is the bug this card exists to prevent, and D13 is explicit that the durable view is what survives a reconnect.
- Adding a Python-generated golden fixture for the Swift DTO test — that file records its own exception to the §12 canonical fixture rule and uses inline JSON because the point of each case is the wire spelling (RealtimeViewDTOTests.swift:4-6). Follow the file.
