# Goal: keyword-ptt-safe-barge-in

## Goal
While Jarvis is speaking, a confirmed user interrupt — a PTT upload, or the wake phrase followed by a configured interrupt keyword recognized on the partial-ASR path inside `candidate_window_ms` when `allowed_barge_mode` is `keyword_two_stage` — cancels the speaking response through the existing generation-scope cancel callable with reason `barge_in`, under that run's own `ResponseInterruptPolicy`, while speaker echo, a wake hit alone, and `output_active` alone can never cancel, and `natural` mode stays unreachable.

## Why
ADR-0006 D8 is the barge-in contract and none of it exists: the voice session's only reaction to active output is to suppress wake detections. D9's mode table and F12 allow exactly two safe stop paths without validated AEC — PTT, and wake-phrase-plus-interrupt-keyword — and this card builds those two and nothing else.

## Target behavior
- **Two spoken stages (ADR-0006 D9 :466).** A new L5 module `jarvis/surface/voice_interrupt.py` owns `BargeInPhase`, `BargeInSignal`, the candidate window, the keyword matcher, and `BargeInRouter`. There is no VAD-candidate stage: no capture frame, energy verdict, or Silero probability can ever open or confirm a barge-in.
  - **Candidate = a wake hit during output.** While `output_active()` is true, `barge_in.enabled`, and `allowed_barge_mode` is `keyword_two_stage`, the wake decision block (jarvis/surface/voice_session.py:1030-1059) no longer drops the detection: it traces `barge_in_candidate`, opens a `candidate_window_ms` window, and arms capture through the existing `_detections` path so the partial-ASR lane runs. Nothing is ducked, nothing is cancelled, and no durable event is written by the candidate.
  - **Confirm = the interrupt keyword on the partial-ASR path.** A partial revision whose normalized text contains any `barge_in.interrupt_keywords` entry, arriving inside an open window, emits exactly one `BargeInSignal(phase="confirmed", confirm_source="keyword")` and the trace `barge_in_confirmed`. Both sides are normalized with the normalizer the partial path already applies (`voice_asr.normalize_partial_text`, jarvis/surface/voice_asr.py:695-698); the keyword match reads the normalized text `UtteranceAssembler._pull_revisions` (jarvis/surface/voice_session.py:785) already computes.
  - **Confirm = a PTT upload during output.** An `/inherent/asr-submit` upload arriving while output is active confirms directly, with no prior candidate and in both modes, as `BargeInSignal(phase="confirmed", confirm_source="ptt")`. A button press is not echo.
  - A window that reaches `candidate_window_ms` with no keyword is dropped as typed telemetry — trace `barge_in_candidate_dropped` plus a counter on `VoiceSessionMetrics` — and produces no cancel (ADR-0006 §6 F11 :651).
  - With barge-in off, or in `ptt` mode, the wake hit stays suppressed exactly as today: same counter, same `audio_input_wake_suppressed` trace, nothing armed.
  - Fail closed on a missing prerequisite: if `allowed_barge_mode` is `keyword_two_stage` while `partial_asr.enabled` is false, the keyword confirm is unavailable — log one warning and accept PTT confirms only.
- **The router is closed and injected.** `BargeInRouter` receives `BargeInSignal`s, deduplicates per candidate window, and calls one injected `interrupt: Callable[[str], str]` bounded by `confirm_timeout_ms`, recording the returned outcome on `barge_in_confirmed`. It never imports `jarvis.decision` or `jarvis.runtime`, never touches actions, and never writes a durable event. `jarvis/surface/voice_session.py` gains only a config field, an optional router handle, the candidate emit in the wake decision block, and the normalized-partial feed out of `_pull_revisions`; it still contains no cancel, flush, or duck token.
- **The interrupt policy is honored, never bypassed (ADR-0006 D8 :418-419).** `ResponseInterruptPolicy.confirmed_playback`'s default becomes `"interrupt_expected_playback_generation"` (jarvis/shared/realtime.py:203) and `start_response_run` issues the policy from that config-carried default (jarvis/decision/response_run.py:683-686). The runtime-side interrupt callable resolves its target from `ResponseRunRegistry.open_runs()`, reads that run's `interrupt_policy`, and acts only when `confirmed_playback` is `interrupt_expected_playback_generation` and `generation_action` is `cancel`; a policy of `ignore`, zero open runs, or more than one open run cancels nothing and returns that outcome string for the trace. The runtime never invents a scope.
- **One interrupt entry point.** A permitted confirmed barge-in calls the existing `make_response_cancel_callable(runtime)(response_id, "generation", "barge_in")` (jarvis/runtime/__init__.py:1646-1708) and nothing else. `"barge_in"` joins `RESPONSE_CANCEL_REASONS` (jarvis/shared/realtime.py:23-25) so the durable `response.cancelled` carries the true reason instead of being normalized to `operator_request`. Playback stop is whatever that cancel path already does once lane A's `_interrupt_active` CAS is on it; this card adds no new public method to `StreamingTTSPipeline` and does not touch `jarvis/surface/voice_media.py` at all.
- **Out-of-band priority.** The interrupt never enters the intent-pump queue (jarvis/runtime/inherent_loop.py:969); it is a direct in-memory call on the control path, the same shape the HTTP cancel route already uses (ADR-0008 §8 barge-in control lane). The interrupting utterance's own transcript still reaches L3 through `utterance.received` unchanged, so a confirmed interruption becomes the next full question (ADR-0006 D8 :419).
- **Mode is read, never resolved.** The allowed mode comes from B2's `DeviceProfileSnapshot.allowed_barge_mode` exposed on the session. `keyword_two_stage` enables the candidate and the keyword confirm; `ptt` leaves the wake suppression untouched so only a PTT upload can confirm; `natural` is treated as `keyword_two_stage` and logs one warning per snapshot change — natural stays unreachable in this card.
- **Config.** `realtime.single_audio_ingress.barge_in.{enabled: false, candidate_window_ms: 1200, confirm_timeout_ms: 800, interrupt_keywords: ["停", "别说了", "stop"]}` parsed by `realtime_input_session_config_from_mapping` into a `BargeInConfig` on `RealtimeInputSessionConfig` (jarvis/surface/voice_session.py:56-72), mirroring `PartialAsrConfig` (:72). Values are D8/D9 candidates, not promises; `confirm_timeout_ms` is the outer bound on the injected callable and sits above the existing `realtime.response.cancel_timeout_ms: 500`. With `enabled: false` behavior is byte-identical to today: no candidate window, no router, no arming during output, no new field on any wire payload.
- **The two existing pins are revised, not deleted, to a stronger invariant:** `output_active` alone, a wake hit alone, and any VAD verdict alone can never cancel; a hard cancel happens only on `BargeInSignal(phase="confirmed")`, which requires a second independent signal (an interrupt keyword inside the window, or a PTT upload) and a permitting `ResponseInterruptPolicy`. The canary keeps its forbidden-token scan and both trace-string assertions (the off path and `ptt` mode still emit them) and gains `request_response_cancel` and `_interrupt_active` to the forbidden set. The wave-3 integration test keeps its existing case unchanged for `barge_in` off and gains a sibling with `barge_in.enabled: true` in `ptt` mode where a wake hit during output still arms nothing and the injected interrupt callable is never called.

## Rejected approaches
- A VAD-based speech candidate during playback (the earlier two-phase draft) — without AEC the speaker's own audio produces speech verdicts constantly, and D9 (:466, :475) requires two *spoken* stages, not one spoken token plus an acoustic guess. Dropped entirely, including the `tts` threshold profile it would have used.
- A single keyword with no wake phrase (bare "停") — D9 rejects it explicitly (:475): Jarvis may say that word itself.
- Reusing `reason="user_stop"` to avoid touching the closed vocabulary — the barge-in row would be indistinguishable from a panel Stop press in the Event Log, which is what the live evidence has to tell apart.
- Routing the interrupt through the intent-pump queue — D8 exists because a stop utterance queued behind the response it should interrupt cannot stop it; ADR-0008 §8 requires an independent highest-priority lane.
- A new press/release wire op for PTT — the WAV upload already proves a deliberate press, needs no Swift change, and cannot be produced by echo.
- A new public `StreamingTTSPipeline.interrupt_active_speech` — lane A's cancel-path `_interrupt_active` CAS already stops playback from the durable cancel, and a second stop entry would race it for the same generation.
- Bypassing `ResponseInterruptPolicy` and always stopping — D8 :418-419 makes the runtime a mechanical applier of the L3-issued policy; making the default permit the interrupt is a one-value config change, while a bypass would make the frozen contract decorative.
