How it's built

Jarvis is one brain and several bodies. The brain is a Python daemon, and the Mac companion and the iPhone, iPad and Apple Watch apps are its bodies; the daemon’s code is split into layers it is not allowed to blur. This page is the map; Design notes tells four of the decisions behind it as stories.

One brain, several bodies

Section titled “One brain, several bodies”

The brain holds the memory, the event log, the model calls and the tools; every other device is one of its terminals (ADR 0170). It can run on a Raspberry Pi at home, and devices reach it only over a private network. Each body keeps its own microphone, wake word and speaker. The iPhone, iPad and watch apps are native SwiftUI; the iPad can also show and drive your Mac’s screen (Jarvis Remote). The rest of this page describes the daemon and the Mac companion.

The daemon and the companion

Section titled “The daemon and the companion”

The daemon is Python 3.12, and it has roles. runtime.role in config/jarvis.yaml is all (one machine does everything, the default) or brain, and a device that only speaks and listens runs the terminal entry instead (ADR 0170). The brain on the Pi is headless: it holds state, model requests and the schedule, touches no microphone or speaker, and gives the model no device-bound tools. A terminal, such as the Mac, keeps the microphone, echo cancellation, wake word, endpointing and playback, and the brain streams the speech to it. The model keys stay on the brain.

Terminals reach the brain over WebSocket, /terminal/ws for the Mac and /phone/ws for the phone. The brain listens on loopback and its Tailscale address, never on 0.0.0.0, and admits a remote device only with that device’s own pairing token.

The companion is Electron with React 19 and TypeScript, plus a small AppKit module (Objective-C++) that draws the glass. It owns what you see on the Mac: the ball beside the notch, the Dashboard, setup and settings. It holds no models and no memory. A small Node host starts beside it when you open the Agents window, to keep your Claude Code and Codex sessions alive across restarts. The iPhone, iPad and Apple Watch apps are native SwiftUI.

On the Mac the companion talks to its local daemon or terminal over loopback with a per-machine key. That endpoint answers only requests addressed to 127.0.0.1 or localhost (so a web page that rebinds its own domain to your machine gets nowhere), and every route except the liveness probe needs the key from the owner’s runtime directory. A terminal answers the few device routes itself, such as dictation, and forwards the rest to the brain. It never answers a question about your state from local data. Measured from the MacBook, the brain took about 80 ms over a Tailscale relay against 3 ms on loopback, which is why captions and the speaking face stay on the terminal.

The voice path

Section titled “The voice path”

Each device finds the wake word on its own. The Mac uses microWakeWord (“Hey Jarvis”); the iPhone and iPad look for it in the words their recognizer is already producing, while the app is on screen. With several devices around, the brain names the one that answers before you speak: the one you are already talking to, or else the one you used last (ADR 0407).

Hearing depends on configuration. When cloud recognition is on, the device streams each utterance to the brain and the brain streams it to Qwen, with the owner’s word list as hot words, so the provider key stays on the Pi. Without it, or without the brain, the Mac hears with SenseVoice and Silero for voice activity detection, on the device. The voice is MiniMax, streamed over WebSocket. Storage is SQLite throughout.

The models are Claude by default: Sonnet for conversation, Opus for the doing lane that writes what you were doing, and Haiku for the frequent background analysts.

Three tiers

Section titled “Three tiers”

The daemon’s code is three tiers, and a package may import only what is below it.

Tier Package Owns Example module
Top runtime Building the process, running it, driving a turn, and the code that needs two blocks at once jarvis/runtime/turn/drive.py
Block decision Tier 0 routing, policy and gates, building each turn’s model request, model calls, the nightly summaries and their schedules jarvis/decision/gates.py
Block execution Tools, workers, the plugin and MCP client, the browser guard jarvis/execution/mcp_tools.py
Block surface Voice, the HTTP and WebSocket interface, pages, pushes, Claude Code and Codex sessions, observers for screen and usage jarvis/surface/voice_pipeline.py
Block deployment The runtime directory, keychain, launchd, sleep and wake, model downloads, export and erase jarvis/deployment/launchd.py
Base state The append-only event log, projections folded from it, memory.db, the settings file and the other local stores jarvis/state/event_log.py
Base shared Pure helpers and static data: the product name, the clock, the language table, prices. Imports nothing. jarvis/shared/pricing.py

jarvis/cli/ (the entry point) sits above runtime.

Only runtime/ joins the blocks

Section titled “Only runtime/ joins the blocks”

Imports run one way. cli may import runtime; runtime may import the four blocks; the blocks may import state; state may import shared; and shared imports nothing. The four blocks cannot import each other, so the voice code cannot reach into the tools and the decision code cannot reach into the voice.

This is a rule the build enforces. lint-imports reads the contract in .importlinter and fails if any package breaks it; it runs in the repository’s setup script and is a gate before every commit. A canary enforces the other half: a module goes in runtime/ only when no single block could hold it, so new code lands in the block it uses. When two blocks have to cooperate, runtime/ hands one a function from the other. For example the decision-snapshot cache lives in jarvis/state/decision_snapshot_cache.py, and the runtime hands each turn a reader from it, so the decision code never learns where it came from.

The state spine

Section titled “The state spine”

Everything Jarvis knows flows one way: event log, then projections, then memory.

  • The event log is a SQLite table that only ever grows. Triggers reject every UPDATE and DELETE; a correction is a new event. Each event records who reported what and when, event types are registered in one file, and large things like screenshots and recordings are stored as files with only a reference in the log.
  • Projections are folds of that log: pending confirmations, open actions, the recent turns. Models, tools and screens cannot write them. Each turn reads the fold up to the latest event, and since ADR 0164 it folds only the events added since the last read, with the same result as folding from the start.
  • Memory is memory.db: the verbatim conversation, the per-day summaries, and the versioned note about you that the night run rewrites. Every layer above it is derived and can be rebuilt.

How decisions are recorded

Section titled “How decisions are recorded”

Every decision that moves a boundary or a contract gets an ADR: more than 400 records so far, one decision per file, one page each. A few of them are public in docs/adr. The standard (docs/adr/README.md) makes an Alternatives rejected section mandatory, with losing reasons someone could refute with a number, because that is the one thing the code and the spec never say. scripts/check_adrs.py checks the format, the status vocabulary, the 200-line cap and dangling references. To change an accepted decision you write a new ADR and mark the old one superseded; you do not edit it.

The full specification

Section titled “The full specification”

What a public build has to satisfy is written down in the specification: processes, the state spine, how a turn is acted on, what leaves the Mac, threats and their guards, keys, lifecycle. It is written in Chinese; the ADRs are in English.
